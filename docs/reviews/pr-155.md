## Review Summary

+253 줄 규모로 DTO·어댑터·렌더러·테스트 두 벌로 구성됩니다.

핵심 메커니즘은 세 계층에 걸쳐 일관되게 적용됩니다. 먼저 `dto.ts`의
`ResearchSummaryDto`에 6개 필드(문자열 2개·배열 3개·리스크 내 배열 1개)를

`?? []`로 정규화하여 `ResearchView`와 `ResearchRisk`에 타입 안전한 형태로
매핑합니다. 마지막으로 `ResearchPage.tsx`는 이를 받아 헤더 스탠스 박스에
`stanceComment`·`confidenceBasis`를, 브리핑 카드 하단에 불릿 그룹 3개를,
리스크 항목에 `근거` 불릿을 렌더하며 — null이거나 빈 배열이면 해당 요소 전체를
생략합니다.

기존 화면과의 하위 호환이 설계 문서의 핵심 요건입니다. 세 불릿 그룹이 모두
비었을 때 브리핑 문단(`body`)만 표시하는 경로는 테스트에서 `NULLS` 픽스처로
명시적으로 단언합니다. `evidence`가 빈 배열이면 `근거` 제목 자체가 렌더되지
않으며, `stanceComment`·`confidenceBasis`는 null이면 해당 `<p>` 태그 전체를
조건 렌더로 생략합니다.

범위 준수 측면에서 `src/features/research/queries.ts`·`src/shared/` 파일은 전혀
변경되지 않았으며, 레이아웃 그리드는 #142(PR #154) 결과를 그대로 유지합니다.

## Suggestions

**S1. DTO의 배열 필드가 BE 실계약보다 넓은 타입으로 선언됩니다**

BE `schema.py`의 `positive_factors`·`caution_factors`·`next_checks`는
`list[str] = Field(default_factory=list)`로 정의되어 있어 절대 `null`을
반환하지 않습니다. 반면 `dto.ts`에서는 `string[] | null`로 선언되어 있습니다.
어댑터에서 `?? []`로 방어하므로 런타임 동작은 정상이고, 실제 BE 응답에서 null이
오지 않으므로 현재 테스트도 통과합니다. 다만 DTO가 실계약보다 허용 범위가 넓어,
미래 개발자가 BE 계약과의 차이를 DTO에서 확인하기 어렵습니다. 엄밀히 맞추려면
`positive_factors?: string[]`(null 제거)로 좁히는 것이 이상적이지만, 실제 영향이
없고 어댑터 방어가 충분하므로 현 범위에서 차단 요인은 아닙니다.

심각도: 비차단, 후속 정리 대상.

**S2. 브리핑 카드 내 소제목이 `<h3>`이나 부모 섹션에 명시적 헤딩이 없습니다**

`ResearchPage` 내 브리핑 카드 `<Card>`는 `<h2>`로 헤드라인을 표시합니다. 그
아래 긍정 요인·주의 요인·다음 확인 사항은 `<h3>`으로 렌더됩니다. 헤딩 레벨
자체는 올바른 계층(`h1 → h2 → h3`)이지만, 브리핑 카드가 `<section>`이 아닌
`<Card>(=<div>)` 요소여서 스크린리더가 헤드라인과 소제목을 명시적 섹션 경계
없이 나열합니다. 한편 리스크 패널 내 `근거` 소제목은 상위 리스크 제목이
`<h3>`이므로 `<h4>`를 쓴 것은 적절합니다. 접근성 우선순위가 높다면 브리핑
카드를 `<section aria-labelledby>` 구조로 보완할 수 있으나, 현재 레이아웃 PR
#154에서도 동일한 `<Card>` 패턴을 쓰고 있으므로 이 PR 범위에서 강제하기보다는
후속 접근성 이슈로 분리하는 것이 적절합니다.

심각도: 비차단, 후속 접근성 이슈 권장.

**S3. 불릿 항목의 `key`가 내용 문자열 자체입니다**

`group.items.map((item) => <li key={item}>{item}</li>)` 패턴은 동일한 문자열이
같은 그룹 내에 두 번 나타날 경우 React key 충돌이 발생합니다. 현재 BE에서
중복 배열 항목을 내보낼 가능성이 낮고 실제 발생 사례가 없어 런타임 오류로
이어지지는 않습니다. 그러나 규칙으로 정착되기 전에 `(item, i) => <li key={i}>` 또는
고유 prefix를 붙이는 방식으로 방어하는 것이 안전합니다. `evidence` 렌더도 같은
패턴을 사용합니다.

심각도: 비차단, 방어적 개선 권장.

## Questions

**Q1. `confidenceBasis`가 헤딩 순서상 `stance` 텍스트보다 먼저 렌더됩니다**

현재 스탠스 박스 DOM 순서는 `신뢰도 배지 → confidenceBasis → stance 라벨 →
stanceComment`입니다. 설계 문서는 "신뢰도 배지 아래(또는 옆)에 confidenceBasis"
라고 기술하므로 명시적 위반은 아닙니다. 다만 사용자 읽기 흐름이 "근거 문장 →
스탠스 라벨 → 한 줄 코멘트" 순이 되어, 스탠스 라벨을 읽기 전에 근거 문장을
먼저 만나게 됩니다. 의도한 UX인지, 아니면 `stance → stanceComment → 배지 →
confidenceBasis` 순으로 변경이 필요한지 확인이 필요합니다.

심각도: 문의(의도 확인 후 디자인 결정).
