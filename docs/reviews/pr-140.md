## Blocking

**B1. `useSaveBuyChecklist`가 두 인스턴스로 분리되어 있고, 메모 debounce effect의 `checkedItemKeys` 의존성이 타이머를 조기 초기화합니다**

`ResearchPage`에서 `checklistMutation`과 `memoMutation`을 각각 `useSaveBuyChecklist(research?.assetId ?? 0)`로 별도 인스턴스로 생성합니다(444–447행). 두 mutation은 독립된 상태를 가지므로 `checklistMutation.isPending`/`variables`가 `memoMutation`의 상태에 영향을 주지 않아 의도된 격리는 달성됩니다. 그러나 debounce effect의 의존성 배열에 `checkedItemKeys`가 포함되어 있습니다(532행). `checkedItemKeys`는 `checklistMutation.isPending`·`variables`·`serverCheckedItemKeys`에서 파생되는 useMemo 값입니다. 따라서 사용자가 메모를 입력한 뒤 debounce 타이머가 작동 중인 상태에서 체크리스트를 토글하면, `checkedItemKeys`가 변경되어 effect가 재실행되고 이전 타이머가 clearTimeout으로 취소된 후 새 타이머가 시작됩니다. 결과적으로 메모 자동 저장이 토글 직후 매번 1초씩 밀립니다. 이것은 사용자 UX 관점에서 의도에 부합하는 동작일 수 있습니다(체크리스트 토글이 곧 PUT을 보내므로 메모 PUT은 직후 따라가는 것이 자연스럽습니다). 그러나 보다 근본적인 문제가 있습니다: `checkedItemKeys`가 메모 debounce의 effect 의존성에 있으면, 체크리스트 토글 시 `checklistMutation.isPending`이 true로 바뀌고 즉시 false로 돌아오는 과정에서 effect가 두 번 재실행됩니다. 첫 번째 실행에서 `checkedItemKeys`가 최신 체크 상태를 가리키므로 메모 저장 body의 `checked_item_keys`는 최신 값으로 전송되어 일관성이 있지만, 타이머 재기동이 debounce 보장을 파기합니다.

더 중요한 경합 시나리오가 있습니다. 체크리스트 토글과 메모 debounce가 동시에 진행 중일 때 두 mutation은 서로의 값을 현재 상태에서 읽습니다. `toggleChecklistItem`(582행)은 `memoValue`를 읽고, debounce 콜백(523행)은 `checkedItemKeys`를 읽습니다. `useSaveBuyChecklist`의 `onSuccess` 콜백이 `['research']` queryKey를 무효화하면 `useResearchView`가 재조회됩니다. 재조회 완료 후 `serverCheckedItemKeys`가 갱신되고, 이때 debounce 타이머가 아직 살아 있다면 effect가 재실행되어 불필요한 PUT이 한 번 더 발생할 수 있습니다. 이 중복 PUT은 최종 상태를 틀리게 만들지는 않지만(幂等성이 있으므로) 불필요한 API 호출입니다.

핵심 문제는 두 mutation 인스턴스가 아니라 debounce effect의 의존성 설계입니다. 설계 문서(`docs/designs/138-research-design-alignment.md`)는 메모 debounce 저장 시 "현재 `checked_item_keys`를 함께 전송"한다고 명시했으나, debounce 타이머가 재기동되어야 한다는 의도는 없습니다. `checkedItemKeys`를 effect 의존성에서 제거하고 ref로 추적하거나, debounce 타이머 내부에서 최신 값을 ref를 통해 읽도록 수정하면 타이머 조기 초기화 없이 최신 checked_item_keys를 동봉할 수 있습니다.

테스트가 이 경합을 커버하지 않습니다. "seeds and automatically saves the memo after one second" 테스트는 체크리스트 토글 없이 메모만 변경하는 경로를 검증합니다.

심각도: 차단. debounce 타이머가 체크리스트 토글마다 초기화되는 것은 핸드오프·설계 문서의 의도("입력 후 1초 debounce")와 다르며, 실 사용에서 메모 저장이 체크리스트 조작이 이어지는 한 지연됩니다.

## Suggestions

**S1. `useSaveBuyChecklist` 두 인스턴스가 하나로 합쳐질 수 있습니다**

현재 `checklistMutation`과 `memoMutation`이 동일한 assetId와 엔드포인트를 대상으로 두 인스턴스를 만들고 있습니다. 인스턴스를 분리한 의도는 체크리스트 낙관적 업데이트(`checklistMutation.isPending`·`variables` 사용)와 메모 debounce 저장을 독립적으로 추적하기 위함으로 보입니다. 이 의도 자체는 타당합니다. 다만 B1을 해결하는 과정에서 checkedItemKeys를 ref로 추적하면 두 인스턴스를 하나로 합쳐도 무방합니다. 하나로 합치면 `onSuccess`에서 중복 무효화가 발생하지 않습니다. 현재 구현에서는 체크리스트 토글이 PUT을 보내고 무효화를 일으키고, 그 직후 메모 debounce PUT도 무효화를 일으키므로 `['research']` queryKey가 짧은 시간 안에 두 번 무효화될 수 있습니다. 심각도: 비차단·B1 수정과 함께 처리 권장.

**S2. `useWatchlistAssets(1, 100)` 호출에서 페이지네이션 범위 내 여부로 관심종목 등록을 판정합니다**

구현자가 스스로 보고한 잔여 위험입니다. `useWatchlistAssets`의 내부를 확인하면(queries.ts 55–80행), `items?page=${page}&size=${size}` 파라미터로 첫 번째 워치리스트의 아이템을 조회합니다. `size=100`을 전달하므로 최대 100개 항목까지만 조회하고, 그 결과에서 심볼 일치 여부로 `registeredWatchlistItem`을 찾습니다. 관심종목이 100개를 초과하면 해당 페이지에 없는 종목은 미등록으로 오판됩니다. 현재 프로덕션 데이터 규모에서는 발생 가능성이 낮고, 기존 훅 계약을 그대로 재사용한 것이므로 구현 범위 내에서의 최선입니다. 다만 watchlist 전용 "단일 종목 등록 여부 확인" API가 없는 현 BE 계약에서 근본 해결은 불가능하므로, 후속 이슈로 BE `GET /watchlists/{id}/items?symbol=` 필터 추가 또는 관심종목 판정 전용 쿼리 신설을 제안합니다. 심각도: 비차단, 현재 규모에서 무시 가능하나 후속 이슈 생성 권장.

**S3. 어댑터 픽스처에서 `checked_item_keys`와 `items[].checked`를 혼용하고 있어 우선순위 규칙을 명시적으로 검증하는 테스트가 없습니다**

`adaptResearchDetail`은 `checked_item_keys`가 존재하면 그 값을 우선하고, 없으면 `item.checked` 폴백을 사용합니다(adapters.ts 166–168행). 테스트 픽스처(`adapters.test.ts`, 53–70행)는 `checked_item_keys: ['valuation']`를 설정하고 `items[0].checked: false`를 두어 id='valuation'이 checked=true로 나오는지를 검증합니다. 이는 우선순위 규칙의 핵심 경로는 커버합니다. 그러나 `checked_item_keys`가 null이거나 빈 배열인 경우 `item.checked` 폴백이 동작하는지를 검증하는 케이스가 없습니다. BE가 `checked_item_keys`를 null로 반환하는 구형 클라이언트 호환 경로가 있을 경우 폴백이 조용히 무시됩니다. 심각도: 비차단·낮은 비용 추가 테스트로 커버 권장.

**S4. `formatSignedCurrency`에서 음수 값의 절댓값을 `formatCurrency`에 전달합니다**

ResearchPage.tsx의 `formatSignedCurrency` 함수는 부호를 수동으로 결정하고 `Math.abs(value)`를 `formatCurrency`에 넘깁니다. `Intl.NumberFormat`은 통화 포맷에서 음수를 자체적으로 처리하지만, 일부 로케일/통화에서 괄호 표기 `($5.25)` 대신 선행 마이너스 `−$5.25`를 출력할 수 있어 외형이 달라집니다. 현재 `'en-US'` 로케일 고정이므로 마이너스 기호가 오게 됩니다. 이 방식은 일관성이 있고 테스트에서도 `-$5.25` 형식으로 단언했으므로 의도적입니다. `try/catch` fallback 분기와 결합하면 코드가 복잡해지지만, 이 수준의 통화 포맷 로직은 현재 요구 사항에 충분합니다. 심각도: 비차단·정보 제공.

## Questions

**Q1. `checklistMutation` 낙관적 업데이트가 `memoMutation` 완료 후 서버 응답과 충돌할 때의 동작은 명세되어 있나요?**

`checkedItemKeys`는 `checklistMutation.isPending` 중에는 낙관적 값을 사용하고, isPending이 false가 되면 `serverCheckedItemKeys`(`research.buyChecklist`의 `checked` 필드 기반)로 돌아갑니다. `memoMutation` 성공 후 `['research']` 무효화로 `useResearchView`가 재조회되면, 새 서버 응답의 `checked_item_keys`가 `adaptResearchDetail`을 통해 `buyChecklist[].checked`로 매핑됩니다. 이 경로에서 BE PUT 응답(`BuyChecklistResponse`)의 `checked_item_keys`가 GET 응답과 항상 동기화되어 있다면 문제없습니다. BE 계약상 PUT은 응답으로 `checked_item_keys`를 포함한 `BuyChecklistResponse` 전체를 반환하므로(`schema.py` 25–31행), onSuccess에서 무효화 대신 응답으로 캐시를 직접 갱신하면 더 안정적입니다. 설계 문서는 "단순 무효화로 동기화한다"고 명시했으나, 이 설계 판단이 이 충돌 경로를 고려한 것인지 확인이 필요합니다. 심각도: 문의.

**Q2. `useWatchlistAssets(1, 100)` 호출이 `ResearchPage` 마운트 시 항상 전체 워치리스트를 조회합니다. 네트워크 비용이 허용 범위인가요?**

리서치 화면이 열릴 때마다 관심종목 등록 여부를 판정하기 위해 `useWatchlistAssets(1, 100)`을 호출합니다. 이 쿼리는 내부적으로 워치리스트 목록 조회 + 아이템 목록 조회 두 번의 API 호출을 순차적으로 실행합니다. 탄탄한 캐싱(`gcTime`/`staleTime`)이 있다면 재마운트 시 네트워크 비용이 없을 수 있지만, 현재 `createTestQueryClient`에서 `gcTime: 0`을 사용하는 것으로 보아 앱 기본 설정에 대한 확인이 필요합니다. 운영 수준에서는 staleTime을 설정해 워치리스트 캐시를 재사용할 것을 권장합니다. 심각도: 문의.

## Final Recommendation

**Blocking 소견 1건이 있습니다. 현재 상태에서 머지를 보류합니다.**

B1(debounce effect의 `checkedItemKeys` 의존성 설계)은 핸드오프 명세 "입력 후 1초 debounce"의 보장을 파기합니다. 체크리스트 토글이 이어지는 한 메모 자동 저장이 지연되며, 추가로 `checklistMutation` 완료 후 무효화로 인한 effect 재실행이 불필요한 PUT을 유발할 수 있습니다. 수정 방향은 `checkedItemKeys`를 debounce effect 의존성에서 제거하고 ref로 추적하는 것입니다.

범위 준수는 양호합니다. 변경 불가 파일 `src/features/watchlist/`와 `src/shared/api/`는 수정 없이 훅만 재사용했습니다. DTO·어댑터·쿼리 변경은 설계 문서 범위 내입니다.

테스트는 대체로 충실합니다. 등락 표시(양·음·null), 기간 탭 전환 재조회, 체크 토글 PUT body 검증, 메모 debounce fake timer, 저장 성공/실패 표시, 관심종목 add/remove 분기를 모두 커버합니다. B1 경합 경로(메모 입력 중 체크리스트 토글)는 커버하지 않으며, 이는 B1 수정 시 함께 추가해야 합니다.

스택 구조 주의: PR #139(feat/137-research-thesis-404-fix)를 먼저 머지한 뒤 이 PR을 병합해야 합니다.

B1 수정 및 재검증 후 머지 가능 판단으로 전환합니다. Suggestions와 Questions는 후속 처리가 가능합니다.
