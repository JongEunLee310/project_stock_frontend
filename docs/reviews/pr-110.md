# PR #110 — 종목 추가 모달 플로우 구현 (feat/108-add-stock-flow)

리뷰어: value-for-fable:itsvff (Sonnet, VFF 위임). 구현: Codex. 브랜치: feat/108-add-stock-flow → main. 관련: FE #108, 핸드오프 task-040.

## Review Summary

PR #110은 이슈 #108에서 요청된 종목 추가 플로우를 구현합니다. `WatchlistPage`의 동작하지 않던 '+ 종목 추가' 버튼에 `AddWatchlistAssetModal`을 연결하는 것이 핵심으로, 신규 컴포넌트 1개(`AddWatchlistAssetModal.tsx`), DTO 3종(`AssetDto`, `CreateAssetBody`, `AddWatchlistItemBody`), 쿼리·뮤테이션 3종(`useAssetSearch`, `useCreateAsset`, `useAddAssetToFirstWatchlist`)이 추가됩니다.

플로우는 두 경로로 나뉩니다. 검색 탭에서는 심볼을 입력하면 350ms debounce 후 `GET /assets?symbol=`을 호출하고 결과 목록에서 종목을 선택해 추가합니다. 검색 결과가 없으면 신규 등록 탭으로 전환해 symbol·name·market 필수, sector 선택 폼을 제출할 수 있습니다. 추가 성공 시 모달이 닫히고 `watchlistQueryKey`(`['watchlist']`) prefix 쿼리 전체가 무효화됩니다. 실패 시 `role="alert"` 오류 메시지가 모달 안에 표시되고 모달은 닫히지 않습니다.

BE 스키마를 직접 대조한 결과, `AssetDto`(FE) ↔ `AssetResponse`(BE), `CreateAssetBody` ↔ `AssetCreate`, `AddWatchlistItemBody` ↔ `WatchlistItemCreate`가 모두 실계약과 일치합니다. 핸드오프 범위 밖 파일은 변경되지 않았으며, `App.test.tsx` 모킹 추가는 기존 테스트 통과를 위한 필수 보완입니다. 기존 테스트는 삭제되거나 약화되지 않았습니다.

## Blocking

**B1: 모달 열릴 때 포커스 이동 미구현**

`AddWatchlistAssetModal`이 `isOpen=true` 상태로 렌더링되면 포커스가 모달 내부로 이동하지 않습니다. 현재 구현에서는 '+ 종목 추가' 버튼(혹은 그 이전 포커스 위치)에 포커스가 유지된 채 모달이 열리므로, 키보드 사용자가 Tab 키로 모달 요소에 접근하기까지 페이지의 수많은 요소를 순회해야 합니다. 스크린리더 사용자에게는 모달 열림 자체가 인지되지 않을 수 있습니다.

ARIA Authoring Practices Guide의 dialog pattern은 `role="dialog"` 요소가 나타날 때 포커스를 모달 내 첫 번째 인터랙티브 요소 또는 dialog 컨테이너로 이동하도록 요구합니다(WCAG 2.4.3). 핸드오프 요구사항에서도 "모달에 적절한 role/aria 속성"을 명시하고 있으므로 포커스 이동은 해당 요건의 범위에 포함됩니다.

수정 방향: dialog 내부 div에 `tabIndex={-1}`을 추가하고 `ref`를 연결한 뒤, `isOpen`이 `true`로 바뀔 때 `useEffect`로 `ref.current?.focus()`를 호출합니다. Tab 키가 모달 밖으로 빠져나가지 않도록 포커스 트랩(focus trap)도 함께 구현하면 키보드 접근성이 완성됩니다.

## Suggestions

**S1: Escape 키 닫기 미구현**

`role="dialog"` 표준 상호작용 패턴에는 Escape 키로 모달을 닫는 동작이 포함됩니다(ARIA APG). 현재 구현에는 keydown 리스너가 없어 키보드 사용자가 Escape로 모달을 벗어날 수 없습니다. `isSubmitting`이 false일 때 Escape → `closeModal()` 를 연결하는 keydown 핸들러를 dialog div 또는 document에 추가하는 것을 권장합니다. B1 수정 시 함께 구현하면 자연스러운 키보드 경험이 완성됩니다.

**S2: WatchlistPage 테스트의 실제 타이머 의존**

`WatchlistPage.test.tsx`의 모달 성공·실패 테스트 두 건이 `window.setTimeout(resolve, 400)`으로 400ms를 실제로 기다립니다. debounce 로직 자체는 `queries.test.tsx`에서 별도 검증되므로 page 테스트에서의 실제 대기는 결정론적이지 않습니다. `vi.useFakeTimers()` + `vi.advanceTimersByTime(400)`으로 전환하면 CI 환경에 관계없이 안정적으로 동작합니다.

**S3: backdrop 클릭으로 닫기 미지원**

외부 overlay div(`role="presentation"`)에 onClick 핸들러가 없어 backdrop 영역을 클릭해도 모달이 닫히지 않습니다. 표준 모달 UX에서는 backdrop 클릭으로 닫히는 동작이 기대됩니다. `isSubmitting` 확인과 함께 backdrop에 `onClick={closeModal}`을 추가하는 것을 권장합니다.

## Questions

**Q1: `useAddAssetToFirstWatchlist` 내 watchlist 재조회**

mutation 실행 시마다 `apiGet('/watchlists?page=1&size=20')`을 직접 호출해 첫 번째 watchlist id를 가져옵니다. TanStack Query 캐시를 경유하지 않으므로 매 mutation마다 실제 네트워크 요청이 발생합니다. 기존 `useWatchlistAssets`도 같은 패턴을 사용하므로 현재 규모에서는 문제가 없습니다. 다만 향후 관심종목 추가 빈도가 높아질 경우 `queryClient.getQueryData`로 캐시를 우선 조회하는 방향이 유리할 수 있습니다. 현재 선택의 이유가 따로 있는지 팀 판단을 묻습니다.
