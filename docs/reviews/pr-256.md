# PR #256 로컬 리뷰 — 판단 복기 작성 화면 (#252)

## Review Summary

판단 기록 재설계 2차 FE의 복기 작성 화면입니다. BE `POST`/`GET /api/v1/decision-logs/{id}/reviews`(`project_stock` #358)를 소비해 판단 복기를 작성·표시합니다.

`features/decision-log`의 `dto.ts`·`adapters.ts`·`queries.ts`에 복기 요청/응답 타입과 `useDecisionReviews(id)`·`useCreateDecisionReview(id)` 훅을 더했습니다. `shared/model`에 `outcomeStatus`·`thesisResult` 한글 라벨 매핑을 추가했습니다. `pages/ui/DecisionReviewPage.tsx`(신규)를 `/decision-log/:id/review` 라우트에 등록하고, 판단 상세(`widgets/decision-detail`)에 복기 화면 진입점을 두었습니다. 복기 폼은 판단 품질(근거 충분성·반대 근거 검토·위험 인식·재검토 명확성·규칙 준수)과 투자 결과(return_rate·benchmark_return_rate·max_drawdown)를 분리된 영역으로 입력하며, `outcome_status`·`thesis_result`는 라벨로 선택합니다.

이번 리뷰는 품질/결과 분리(설계 §14), BE 계약 소비, enum 라벨화, 라우팅을 축으로 봤습니다.

## Blocking

None.

## Suggestions

**S1. 복기 후 판단 상태 전이는 BE 소관 — FE는 무효화로 반영, 정상.** 복기 작성 시 판단 상태가 `REVIEWED`로 바뀌는 것은 BE(#358)가 처리하며, FE는 복기·판단 쿼리를 무효화해 최신 상태를 다시 가져옵니다. FE에서 상태를 낙관적으로 앞서 바꾸지 않아 계약과 어긋날 여지가 없습니다. 현재 구현이 적절합니다.

## Questions

**Q1. 품질과 결과가 화면에서 분리되어 있는가.** `DecisionReviewPage`가 품질 항목과 결과 지표를 별도 영역으로 입력받아 각각 `process_quality`·`result_metrics`로 전송함을 확인했습니다. 설계 §14의 분리 원칙이 UI와 전송 모두에서 지켜져 해소됐습니다.
