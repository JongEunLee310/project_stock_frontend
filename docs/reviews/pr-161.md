# PR #161 로컬 리뷰 — feat: 가격 차트 고도화 — 거래량·MA20·벤치마크 비교

리뷰어: Claude Code — VFF(Sonnet) 위임 교차 리뷰. 구현에 관여하지 않음.

구현자: Codex(gpt-5.6-sol), 커밋 `2b8640e`

## Review Summary

이슈 #148의 구현입니다. 리서치 상세 가격 탭을 가격 라인·MA20·거래량 서브차트로
고도화하고, 벤치마크 비교 토글을 추가합니다. 변경은 14개 파일, +665/-48줄입니다.

구조는 세 레이어로 나뉩니다. 공유 UI 레이어에서는 `LineChart`와 `BarChart`의 포인트
타입을 `Record<string, number | string | null>`로 확장하고, `LineChart`에 `series?`
prop을 additive로 추가해 다중 시리즈를 지원합니다. 기존 단일 시리즈 API(`yDataKey`·
`color`)는 `series`가 없을 때 폴백으로 그대로 동작합니다. 어댑터 레이어에서는
`PriceBarDto`에 `date`·`volume`을 추가하고, `PriceSeriesView`에 `points` 배열을
신설합니다. MA20은 순수 함수 `withMovingAverage`에서 파생하며, 20개 미만 구간은
`null`을 유지합니다. `adaptBenchmarkComparison`은 API 응답 순서를 그대로 유지해
`BenchmarkSeriesItem[]`으로 변환합니다. 페이지 레이어에서는 `PriceSparkline`에
`isBenchmarkEnabled` 상태와 `useBenchmarkComparison` 훅을 결합해 가격 모드와 비교
모드를 전환합니다. 비교 ON일 때만 벤치마크 쿼리를 조회하고(`enabled` 게이트),
1D 전환 시 비교를 자동 해제합니다. 벤치마크 오류는 `ErrorState`로 패널 내에
격리하여 가격 모드나 페이지 나머지에 전파되지 않습니다.

## Blocking

**B1. `BenchmarkComparisonDto.return_percent` 타입이 BE 계약과 불일치합니다**

PR 요청에 명시된 BE 계약은 `return_percent`를 `decimal str`로 정의합니다.
그러나 `src/features/research/dto.ts` 129행에서 `return_percent: number`로 선언하고,
`src/features/research/adapters.ts` 323행에서 `parseDecimal` 없이 `returnPercent:
point.return_percent`를 직접 할당합니다. BE가 실제로 숫자 JSON을 반환한다면 지금
동작하겠지만, decimal str을 반환하는 경우 `returnPercent`가 문자열로 흘러들어
Recharts 렌더링에서 숫자 계산이 깨집니다. 현재 테스트 픽스처는 `return_percent: 0`
(숫자 리터럴)을 사용하고 있어 계약 불일치를 검출하지 못합니다. 다른 모든 decimal
필드(close·revenue·eps 등)가 `parseDecimal`을 통해 변환되는 프로젝트 패턴과도 일관성이
없습니다. BE 계약이 decimal str을 반환한다면 `dto.ts`를 `return_percent: string | null`로
수정하고 어댑터에서 `parseDecimal`을 거쳐야 합니다. BE가 숫자 JSON을 반환한다면
BE 계약 표기를 정정해야 하며, 어댑터 테스트 픽스처에서 계약 형태를 명확히 확인할
수 있도록 주석이나 타입을 명시하는 것이 좋습니다. 심각도: 차단 — BE 실계약 확인
후 어느 방향이든 수정 필요.

## Suggestions

**S1. 가격 모드 LineChart에 `showAxes`가 명시되지 않아 축이 표시됩니다**

기존 가격 차트 코드는 `showAxes={false}`를 전달하여 x/y 축을 숨겼습니다.
신규 `LineChart` 호출(`ResearchPage.tsx` 314행)에서는 `showAxes` prop이 없어
기본값 `true`가 적용됩니다. 설계 문서에 축 표시 여부가 명시되어 있지 않고,
벤치마크 차트와 통일된다는 측면에서 허용 가능하지만, 의도적 변경인지 기존 스타일에서
벗어난 것인지 구현자가 확인하면 좋겠습니다. 심각도: 비차단·디자인 확인 요청.

**S2. `benchmarkQuery.error.message`가 `Error` 인스턴스가 아닌 경우 빈 문자열을 표시합니다**

`ResearchPage.tsx` 245행에서 `benchmarkQuery.error.message`를 직접 `ErrorState`의
`description`에 전달합니다. TanStack Query v5에서 `isError=true`이면 `error`는
타입상 `Error`로 narrowing되어 런타임 안전성은 확보됩니다. 다만 API 오류가
`ApiError` 같은 커스텀 클래스로 throw될 경우 `message`가 빈 문자열일 수 있습니다.
기존 `useValuationMetrics`·`useEarningsSummary`와 동일한 패턴이라 일관성 기준에서는
문제가 없습니다. 오류 메시지 표기 정책이 프로젝트 전반에서 결정되기 전까지는 현재
수준으로 유지하는 것이 적절합니다. 심각도: 비차단·정보 제공.

**S3. 비교 데이터 합산 방식이 첫 번째 시리즈의 날짜 목록에 의존합니다**

`ResearchPage.tsx` 175행에서 `benchmarkSeries[0]?.points.map((point) => point.date)`를
x축 기준으로 삼습니다. BE 계약에서 세 시리즈의 날짜 축이 동일하다고 보장하므로
정상 경로에서는 문제가 없습니다. 그러나 BE 오류 또는 미래 계약 변경으로 시리즈 간
날짜가 어긋날 경우 조용히 일부 데이터가 누락됩니다. 현재 계약 보장 범위 내에서는
허용 가능하며, 차후 계약이 완화되면 날짜 합집합 방식으로 전환을 검토할 수 있습니다.
심각도: 비차단·향후 고려 대상.

## Questions

**Q1. `return_percent` 필드가 BE에서 실제로 숫자 JSON으로 반환되는지 확인을 요청합니다**

## Final Recommendation

Blocking 1건이 있습니다. B1(`return_percent` 타입 불일치)을 해소한 뒤 머지를
권장합니다.

B1을 제외한 구현은 설계 명세를 충실히 따릅니다. MA20 경계값 로직(`index <
MOVING_AVERAGE_WINDOW - 1`)이 정확하며 테스트로 검증되었습니다. `LineChart` series
확장이 additive하게 이루어져 기존 소비처(`DashboardPage`·`PortfolioPage`의 `BarChart`,
기존 LineChart 사용처)를 깨지 않습니다. 벤치마크 오류 격리와 가격 모드 복귀, 1D에서의
자동 해제, `aria-pressed` 토글이 모두 테스트로 확인됩니다. 밸류에이션·실적 탭과
다른 페이지는 변경되지 않았습니다.

`App.test.tsx`·`WatchlistPage.test.tsx`의 변경은 신규 훅 mock 추가로, 해당 페이지
렌더에 영향이 없음을 확인하는 정당한 범위 내 수정입니다.

최종 머지 권한은 개발자에게 있습니다.
