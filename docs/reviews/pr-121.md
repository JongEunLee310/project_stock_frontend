# PR #121 — 관심 종목 페이지 Phase 3 (feat/117-watchlist-phase3)

리뷰어: Claude Code (Sonnet / Value-for-Fable). 구현: Codex (GPT-5, medium). 브랜치: feat/117-watchlist-phase3 → main. 관련: FE #117, 설계 docs/designs/117-watchlist-phase3.md, 핸드오프 .codex/tasks/task-046-watchlist-phase3.md.

## Review Summary

설계 §1–§6의 모든 Decisions가 구현에 반영되었으며, BE 계약 리터럴과의 정합성도 확인됩니다.

주요 변경 내용은 다음과 같습니다. `dto.ts`에 `WatchlistItemEvaluationDto`, `WatchlistEvaluationsResponseDto`, `BuyReadinessDto` 세 인터페이스가 추가되고 `WatchlistSummaryDto`에 `buy_readiness?` 필드가 추가됩니다. `adapters.ts`에는 `evaluationBadgeClassNames` 상수로 Tailwind 클래스를 중앙 집중화한 뒤, `resolveNewsRiskBadge`·`resolveValuationBadge`·`resolveThemeHeatBadge`·`resolveAiJudgmentBadge` 네 resolver를 기존 `resolveStatusBadge` 패턴과 동일한 시그니처로 구현합니다. 알 수 없는 enum 값은 각 resolver의 catch-all 분기에서 중립 폴백을 반환하며 런타임 에러를 발생시키지 않습니다. `adaptWatchlistEvaluations`는 `items`를 `symbol` 키로 reduce해 O(1) 조회 맵을 생성하고, `adaptBuyReadiness`는 `cash_weight` decimal 문자열을 `parseDecimal`로 파싱하며 null 시 0으로 폴백합니다.

`queries.ts`의 `useWatchlistEvaluations`는 `useWatchlistSparklines`의 자기 해결 패턴을 그대로 따릅니다. `/watchlists?page=1&size=20`으로 첫 번째 관심목록 ID를 내부 조회한 뒤 `/watchlists/{id}/evaluations`를 호출하며, `staleTime`은 LLM 응답 비용을 감안해 10분으로 설정합니다. 관심목록이 없으면 빈 map과 `needsResearchCount: 0`을 즉시 반환해 페이지 렌더링 중단을 방지합니다.

`WatchlistPage.tsx`에는 세 상태(로딩·에러·정상)를 일관되게 처리하는 `EvaluationBadgeCell` 컴포넌트가 추가됩니다. 로딩 중에는 배지 셀에만 `<Skeleton className="h-4 w-12" />`를 표시하고, 에러 또는 symbol이 map에 없으면 `—`을 표시하며, 기존 종목·상태·현재가 등 items 기반 컬럼은 두 경우 모두 정상 렌더링을 유지합니다. 컬럼 수가 8 → 12로 증가함에 따라 `colSpan`과 테이블 최소 너비(`min-w-[58rem]` → `min-w-[82rem]`)도 함께 갱신됩니다. 요약 카드 그리드는 `md:grid-cols-2 xl:grid-cols-4`로 변경되고, 에러 상태 카드의 `col-span`도 `xl:col-span-4`로 정확히 갱신됩니다.

테스트는 핸드오프 Test Requirements의 항목 전체를 커버합니다. 기존 `WatchlistSummaryView` 픽스처에 `buyReadiness` 필드가 추가되면서 `watchlistSummaryQueryState`에 TypeScript explicit type annotation이 붙었고, `satisfies WatchlistSummaryView` 키워드로 fixture 타입 안전성이 보강되었습니다.

## Suggestions

**S1 · `beforeEach` 리셋 블록의 enum 출처 주석 누락 (비차단, 테스트 일관성)**

`WatchlistPage.test.tsx`의 최초 `watchlistEvaluationsQueryState` 정의(약 151행)에는 `// app/domains/watchlists/types.py` 출처 주석이 NVDA 픽스처 enum 리터럴에 기재되어 있습니다. 그런데 `beforeEach` 리셋 블록(약 519행)에서 동일 리터럴을 재할당할 때는 해당 주석이 빠져 있습니다. 핸드오프 요건("픽스처 enum 리터럴에 출처 주석 기재")의 취지는 enum 값과 BE 계약 출처를 한눈에 연결하는 데 있으므로, 리셋 블록에도 동일하게 기재하면 일관성이 높아집니다. 현재 커버리지 수준에는 영향이 없어 블로커는 아닙니다.

**S2 · `resolveValuationBadge`·`resolveThemeHeatBadge`의 암묵적 catch-all (비차단, 스타일 비대칭)**

`resolveNewsRiskBadge`는 `HIGH`·`LOW`·`MEDIUM` 세 값을 모두 명시적으로 처리하고 그 외 값만 폴백으로 흘립니다. 반면 `resolveValuationBadge`는 `HIGH`·`LOW`만 명시하고 `MODERATE`를 catch-all에 맡기며, `resolveThemeHeatBadge`도 `OVERHEATED`·`COLD`만 명시하고 `NEUTRAL`을 catch-all에 맡깁니다. `MODERATE`와 `NEUTRAL`의 라벨·색상이 각 resolver의 폴백과 동일하기 때문에 동작은 설계 §1 테이블과 일치하며, `resolveAiJudgmentBadge`도 `STABLE`이 폴백과 동일한 값이라 같은 방식을 취합니다. 기능적으로는 문제가 없지만, resolver 간에 구조가 비대칭입니다. 알려진 enum 값을 전부 명시적으로 분기하면 추후 enum 변경 시 누락을 타입 레벨에서 포착하기 어렵다는 한계는 있으나, 명시적 분기 쪽이 의도를 더 직접적으로 드러냅니다. 현재 범위 내에서 허용되며 후속 리팩터링 기회에 검토할 수 있습니다.
