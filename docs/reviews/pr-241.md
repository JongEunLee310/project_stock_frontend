리뷰는 두 축으로 봤습니다. 분할이 단언을 잃지 않고 파일 간 상태 간섭을 만들지 않는지, 그리고

## Suggestions

**S1. 분할이 flakiness를 해소했다는 근거는 없습니다 — 유지보수성 이득만 인정하는 편이
정확합니다.** 이슈 #236은 분할을 주 범위로 두고 재현이 남으면 `testTimeout`을 올리는 순서로
설계됐는데, 실제로 해소한 것은 타임아웃 상향입니다. 분할 직후 재현됐다고 판단한 근거가
오염된 측정이었기 때문에(아래 Q1) 분할의 효과는 측정되지 않은 상태입니다. 분할 자체는 파일당
관심사가 좁아져 어느 파일을 봐야 하는지 분명해지는 이득이 있으므로 되돌릴 이유는 없습니다.
다만 이 PR을 "분할로 flakiness를 고쳤다"로 기록하지 않는 편이 낫고, PR 본문도 그렇게 쓰여
있습니다.

**S2. `PortfolioPage.test.tsx`·`DecisionLogPage.test.tsx`는 그대로입니다 — 이번 범위 밖이며
타임아웃 상향으로 함께 완화됩니다.** 두 파일도 같은 위험대로 지목했었는데, 개별 테스트 최장
소요는 1초 미만이어서 10000ms 아래에서 여유가 충분합니다. 분할이 필요해지면 이번 헬퍼 구조를
본떠 진행하면 됩니다.

## Questions

**Q1. 최초에 `testTimeout: 20000`을 넣은 근거가 무엇이었는지 확인이 필요했습니다.** 중간 커밋
`bb334b4`는 "실측 최장 5390ms"를 근거로 20000을 넣었습니다. 확인 결과 그 측정은 orchestrator가
재현 실험용으로 띄운 부하 프로세스가 회수되지 않고 누적된 상태에서 이뤄졌습니다. 프로세스를
정리한 뒤 같은 테스트를 다시 재니 313ms였고, 스위트 전체에서 가장 느린 개별 테스트는
1805ms였습니다. 마지막 커밋 `d7cba3a`에서 10000ms로 조정했으며, 이는 실측 최장의 약 5.5배
여유입니다. 해소됐습니다.

**Q2. 타임아웃을 늘리면 멈춘 테스트의 감지가 늦어지는데 허용 범위인지 판단이 필요했습니다.**
10000ms는 최장 테스트의 5.5배여서 정상 소요와 이상 정지를 가르는 경계로 충분히 좁습니다.
20000ms였다면 11배로 벌어져 진짜 정지를 20초간 기다리게 됩니다. 개발자와 상의해 10000으로
정했습니다. 해소됐습니다.
