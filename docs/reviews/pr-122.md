# PR #122 — 빠른 감시 설정 패널 (feat/120-quick-watch-panel)

리뷰어: Claude Code (Sonnet / Value-for-Fable). 구현: Codex (GPT-5, medium). 브랜치: feat/120-quick-watch-panel → main. 관련: FE #120, 설계 docs/designs/120-quick-watch-panel.md, 핸드오프 .codex/tasks/task-047-quick-watch-panel.md.

## Review Summary

설계 §1–§5의 모든 Decisions가 구현에 반영되었으며, BE 계약 리터럴과의 정합성도 확인됩니다.

변경 내용은 다음과 같습니다. `src/features/watchlist-alert-templates/` 디렉터리를 신규 생성하고 dto·adapters·queries·QuickWatchPanel과 각 테스트 파일 총 6개를 추가합니다. `WatchlistPage.tsx`에는 import와 aside 안 삽입 2줄만 추가되며, 기존 테스트 3개 파일(`App.test.tsx`·`DashboardPage.test.tsx`·`WatchlistPage.test.tsx`)에는 `watchlistQueryKey` 내보내기와 `watchlist-alert-templates/queries` mock이 각각 보강됩니다.

데이터 흐름의 핵심 메커니즘은 다음과 같습니다. `watchlistAlertTemplatesQueryKey`를 `queries.ts` 하나에서 `[...watchlistQueryKey, 'alert-templates'] as const`로 정의하고 GET 훅(`queryKey`)과 mutation `onSuccess`의 `setQueryData` 두 곳이 이 상수를 공유하므로, setQueryData 직접 갱신이 올바르게 동작합니다. 타일별 pending 처리는 `pendingType: string | null` state와 mutate 호출 시 전달하는 `{ onSettled: () => setPendingType(null) }` 옵션으로 구현됩니다. `onSettled`는 성공·실패 모두에서 호출되므로 설계 §2의 `onError` 초기화 요건을 포함하며, 설계보다 방어적입니다. watchlist가 없을 때는 GET 쿼리와 mutation mutationFn 모두 watchlistId가 null이면 빈 배열을 즉시 반환해 에러를 발생시키지 않습니다.

`label`과 `condition_description`은 BE 응답값을 그대로 렌더링하며 FE 하드코딩이 없습니다. 아이콘과 활성 클래스만 `TEMPLATE_VISUAL_MAP`에서 매핑되고, 지도에 없는 `template_type`에 대한 `fallbackVisual`이 컴포넌트 내부에 방어적으로 정의되어 있습니다.

## Suggestions

**S1 · 버튼 활성 상태의 `aria-pressed` 누락 (비차단, 접근성)**

`QuickWatchPanel.tsx`의 타일 `<button>`은 활성 상태를 `TEMPLATE_VISUAL_MAP[...].activeClassName`의 색상 클래스로만 표현합니다. `aria-pressed` 속성이 없어 스크린리더 사용자에게는 현재 토글 상태가 전달되지 않습니다. `<button ... aria-pressed={template.isActive}>` 한 줄 추가로 시각 외 채널에도 상태를 전달할 수 있습니다. 이슈 #120에서 접근성이 명시적 요구사항은 아니었으므로 블로커는 아니며, 후속 접근성 이슈로 추적하거나 이번 브랜치에서 바로 추가하는 두 방법 모두 가능합니다.

**S2 · `QuickWatchPanel.test.tsx` 픽스처 출처 주석 형식 미세 차이 (비차단, 일관성)**

`adapters.test.ts`와 `queries.test.tsx`의 픽스처 출처 주석은 `// app/domains/watchlists/types.py` 형식을 사용합니다. 반면 `QuickWatchPanel.test.tsx`의 같은 주석은 `// template_type 원본: app/domains/watchlists/types.py`로 쓰여 있습니다. 출처 파일이 명확히 기재되어 핸드오프 요건의 취지는 충족하지만, 팀 내 주석 형식을 통일하면 grep으로 출처를 조회할 때 더 편리합니다. 동작·커버리지에 영향이 없어 블로커는 아닙니다.

## Final Recommendation

**Blocking 없음. Suggestions 2건, 모두 비차단입니다.**

설계 §1–§5의 모든 Decisions가 구현에 반영됩니다. `watchlistAlertTemplatesQueryKey` 상수를 GET 훅과 mutation이 공유하므로 setQueryData 직접 갱신이 캐시 키 불일치 없이 동작하며, 이는 핸드오프 Risk Level에서 지목한 핵심 위험이 해소된 것입니다. PUT body(`{ templates: [{ template_type, is_active }] }`)가 BE 계약(`WatchlistAlertRuleTemplateBulkRequest`)과 일치하고, enum 리터럴 4종(`PRICE_SPIKE`·`NEWS_RISK_HIGH`·`AI_JUDGMENT_CHANGE`·`THEME_OVERHEAT`)이 `app/domains/watchlists/types.py` 출처 주석과 함께 픽스처에 기재되어 있습니다. `pendingType` + `onSettled` 패턴이 타일별 disabled 처리를 구조적으로 보장하며, `pendingType` disabled 테스트가 이를 실행 수준에서 확인합니다. `WatchlistPage.tsx` 수정은 명세한 2줄에 한정되어 범위 통제 요건을 충족합니다. 4종 CI 검증을 실측으로 확인했습니다.

S1·S2는 접근성 보완 및 코드 일관성 관련 제안이며, 이번 브랜치에서 수정하거나 후속 이슈로 추적하는 방법 모두 가능합니다.

**최종 머지 권한은 개발자에게 있습니다.**
