## Review Summary

F1이 세운 `alertKeys`·adapter 기반 위에 알림 규칙 관리 UI를 얹는 조각입니다. 규칙 CRUD
쿼리·뮤테이션, 조건 자연어 번역 유틸, 목록 테이블 위젯, 생성/수정 drawer를 신설합니다.

핵심은 세 축입니다. 첫째, 조건을 사용자에게 JSON이 아니라 자연어로 보여주는
`conditionText.ts`가 metric·operator·value 전 조합과 복합(`all`) 조건을 한국어 문구로
번역합니다. 둘째, `client.ts`에 `apiPatch`를 추가하고(BE update가 PATCH) 204 No Content
응답을 `{ data: undefined }`로 처리해(규칙 삭제) 핸드오프에서 지목한 두 통합 공백을 메웁니다.
셋째, 빌더 drawer가 템플릿 카탈로그(활성만 선택 가능)에서 출발해 대상·조건·채널·cooldown·
delivery_policy를 조정하며, BE 조건 검증 규칙(TOPIC_IMPACT_SCORE 생성 불가, CHANGED 지표는
operator 고정·값 없음, POSITION_WEIGHT 0~1 범위)을 UI 제약으로 그대로 반영합니다.

기존 관례를 잘 따릅니다: DTO(snake)→`adapt*`→도메인(camel) 매핑, `@/shared/ui`의 `Table`·
`Badge`·`Input`·`Button` 재사용, 중요도 색상은 배지에만 제한. 구 인박스(`AlertsPage`)·요약
카드·사이드바는 무변경으로 병존합니다. 뮤테이션 성공 시 `alertKeys.rules`·`overview`를
invalidate합니다.

## Suggestions

**S1. 빌더의 폼 로드 effect가 `templates` 배열 참조에 의존해, 드러워가 열린 동안 템플릿
쿼리가 refetch되면 폼이 초기화될 여지가 있습니다.** `AlertRuleBuilder.tsx`의 `useEffect`
의존성에 `templates`가 포함되어, 참조가 바뀌면 create 모드는 첫 활성 템플릿으로, edit 모드는
원본 규칙 값으로 폼을 다시 채웁니다(`useAlertRuleTemplates`가 매 fetch마다 `data.map(...)`으로
새 배열을 만들기 때문). 다만 QueryClient 기본값이 `refetchOnWindowFocus: false`·
`staleTime: 30_000`이라 드러워가 열려 있는 동안 템플릿이 자발적으로 refetch되지 않으므로,
실제로 effect는 드러워를 열 때만 발동하며 그때의 초기화는 의도된 동작입니다. 현재 범위에서
문제가 드러나지 않으나, F3에서 폼 상태가 커지기 전에 의존성을 `isOpen`·`mode`·`rule` 중심으로
좁히는 것을 권합니다.

**S2. 행 동작 버튼이 `isActionPending`으로 전역 비활성화됩니다.** `AlertRuleTable.tsx`에서
pause/resume/delete 중 하나라도 in-flight면 모든 행의 동작 버튼이 함께 비활성화됩니다. 중복
요청을 막는 안전한 선택이지만, 한 규칙을 조작하는 동안 다른 규칙 조작이 잠깁니다. 목록이
길어지면 행 단위 pending으로 좁히는 편이 낫습니다. 안전성 문제는 아니므로 후속 판단 사항입니다.
