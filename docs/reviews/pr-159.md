## Review Summary

이슈 #150의 구현입니다. 리서치 상세 화면 aside에 두 개의 신규 카드를 추가합니다.
하나는 `GET /assets/{asset_id}/research-coverage` 계약을 소비해 5개 축별 수집
현황을 보여 주는 "데이터 커버리지" 카드이고, 다른 하나는 기존
`research-summary` 응답의 additive 필드인 `counter_view: string[]`을 표시하는
"반대 관점" 카드입니다. 변경은 9개 파일, +456줄입니다.

구조적으로는 PR #157·#158(뉴스·공시·촉매)이 확립한 카드 독립 쿼리 패턴을
따릅니다. `useResearchCoverage(assetId)` 쿼리는 `useResearchView`와 분리되어
동작하며, 카드 단위 로딩 스켈레톤·오류 ErrorState(재시도)를 갖추어 커버리지
API 실패가 페이지 나머지 렌더를 막지 않습니다. 반대 관점 카드는 별도 쿼리가
없으므로 페이지 로딩에 포함됩니다.

어댑터 레이어에서는 5개 axis 값을 한국어로 매핑하는 `researchCoverageAxisLabels`
상수를 두고, 알 수 없는 값은 axis 원문 폴백으로 처리합니다. `lastUpdatedAt`은
`formatKstDateTime` 적용 후 저장하고, null이면 그대로 null을 유지합니다.
`ResearchView`에 `counterView: string[]`을 추가하고 `adaptResearchDetail`에서
`summary.counter_view ?? []`로 폴백합니다.

aside 배치 순서는 브리핑 → `CounterViewPanel` → `RiskPanel` →
`ResearchCoveragePanel`으로, 설계 문서에서 확정한 순서(브리핑 → 반대 관점 →
리스크 → 커버리지)와 일치합니다.

## Blocking

**B1. `ResearchPage.test.tsx` `beforeEach` 픽스처의 `axis` 필드가 BE 계약 형태를 위반합니다**

`ResearchPage.test.tsx` `beforeEach`(diff +502~+508행)의 나머지 3개 축 항목을
`['실적', '밸류에이션', '공시'].map(axisLabel => ({ axis: axisLabel, ... }))`로
생성해, `axis` 필드에 한국어 axisLabel이 들어갑니다. BE 계약과 `ResearchCoverageDto`
스펙 모두 `axis`는 영문 enum 값(`'EARNINGS'` / `'VALUATION'` / `'DISCLOSURE'`)이어야
합니다. `CoverageAxisRow`는 `item.axis`를 React key로 사용하고,
`adaptResearchCoverage`가 실제로 어댑트한 형태와도 다릅니다.

이 오류가 테스트 실패로 드러나지 않는 이유는 해당 픽스처를 소비하는 단언들이
`axisLabel`·`isCollected`·`lastUpdatedAt` 등의 파생 필드를 검증하고 `axis`
원값 자체를 단언하지 않기 때문입니다. 그 결과 테스트는 통과하지만, 픽스처가
BE 실응답 형태를 반영하지 못해 계약 회귀를 잡아 주지 못하는 구조가 됩니다.
`['EARNINGS', 'VALUATION', 'DISCLOSURE'].map(axis => ({ axis, axisLabel: ..., ... }))`
형태로 수정해야 합니다. 심각도: 차단 — 품질 규율(픽스처는 BE 실계약 형태여야
함)을 직접 위반합니다.

## Suggestions

**S1. `isCollected: true`이면서 `lastUpdatedAt`이 null인 엣지 케이스를 테스트가 다루지 않습니다**

`CoverageAxisRow`는 `isCollected`가 true일 때 `item.lastUpdatedAt ?? '-'`로
폴백 처리합니다. 현재 BE 설계상 COLLECTED 상태이면 반드시 `last_updated_at`이
존재하지만, 미래의 계약 변경이나 파이프라인 오류 시 이 조합이 발생할 수 있습니다.
어댑터 테스트(`adapters.test.ts`)나 페이지 테스트에 해당 케이스를 한 건 추가하면
폴백이 검증됩니다. 이슈 #150 범위에서 명시적으로 요구된 항목은 아니며, 현 시점에
머지를 막는 결함이 아닙니다. 심각도: 비차단·향후 보완 대상.

**S2. `coverageQuery.error.message`의 description 전달이 빈 문자열일 때를 처리하지 않습니다**

`ResearchCoveragePanel`에서 `ErrorState`의 `description` prop으로
`coverageQuery.error.message`를 그대로 전달합니다. `new Error('coverage failed')`처럼
구체적인 메시지가 있으면 문제없지만, 일부 네트워크 오류는 빈 문자열 메시지를
반환할 수 있습니다. 기존 `NewsDisclosurePanel`·`CatalystTimelinePanel` 패턴과의
일관성 여부를 구현자가 확인하면 됩니다. 심각도: 비차단·패턴 일관성 확인 권장.

## Questions

**Q1. `ResearchCoveragePanel`의 헤딩 `h2`가 `section` 롤을 가진 요소의 직접 자식인지 확인이 필요합니다**

`CoverageAxisRow`는 `<li>` 요소를 반환하고 `Card`가 `<section>`을 렌더한다고
가정하면 접근성 구조는 적절해 보이지만, `Card` 컴포넌트가 실제로 `section` 롤의
요소를 렌더하는지 diff만으로는 확인할 수 없습니다. 기존 카드들과 동일한 `Card`
컴포넌트를 사용하므로 문제 없을 가능성이 높지만, 페이지 테스트에서
`.closest('section')`으로 카드를 찾는 방식이 이미 동작하므로 실질적으로는
검증된 것으로 봐도 무방합니다. 구현자가 의도를 명확히 공유해 주면 기록이
깔끔해집니다.
