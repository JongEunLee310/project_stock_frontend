## Review Summary

PR #220에서 `research.briefing`이 있으면 headline + body 전문 + 긍정/주의/다음확인
리스트 3종을 무조건 펼쳐 보여주던 것을, 기본 상태에서는 headline + body 2줄 요약만
보이도록 축약하고 카드 하단 토글로 전문을 펼치는 기능입니다.

`ResearchPage.tsx`에 카드 로컬 상태 `isBriefingExpanded`(`useState<boolean>`, 기본
`false`)를 신설했습니다. body 문단은 `line-clamp-2` 클래스를 접힘 상태에서만 붙이는
방식으로 상시 DOM에 남아 있고, 리스트 3종 블록은 `isBriefingExpanded ? [...].map(...) :
null` 삼항으로 감싸 접힘 상태에서는 배열 자체가 렌더되지 않습니다. 즉 body는 CSS
클램프, 리스트는 조건부 렌더라는 서로 다른 방식이 적용되어 있고, 둘 다 목적에 맞는
선택입니다. 토글 버튼은 `aria-controls="research-briefing-content"`(클램프 문단과
리스트를 감싸는 `div`의 id)와 `aria-expanded={isBriefingExpanded}`를 갖고, 라벨은
접힘 시 `더 보기 ›`(화살표는 `aria-hidden`), 펼침 시 `접기`로 바뀝니다. 이 버튼의
클래스명과 `더 보기 <span aria-hidden="true">›</span>` 구조는 같은 파일의 뉴스·공시
카드 '더 보기' 링크(`ResearchPage.tsx:1383` 근처)와 동일해 핸드오프가 요구한 기존
패턴 재사용이 그대로 지켜졌습니다.

헤더의 'AI briefing' 라벨과 `갱신 {createdAt}` 표시, 저장본 부재 시 `EmptyState` +
생성 버튼 분기는 diff 범위 밖에 있어 그대로 유지됩니다. 변경은 `research.briefing ?
(...) : (...)`의 값 있는 분기 안쪽으로만 제한되어 있고, 스코프 밖 파일이나 다른
카드는 건드리지 않았습니다.

테스트는 기존 `renders all structured briefing groups as bullet lists`를 `clamps
briefing details by default and toggles the full content`로 확장해, 기본 상태에서
body가 `line-clamp-2` 클래스를 갖고 리스트 3종 텍스트가 `queryByText`로 문서에 없음을
확인한 뒤, 토글 클릭 후 클램프 클래스가 사라지고 리스트가 `findByText`로 나타나며,
다시 접었을 때 리스트가 사라지는 왕복까지 검증합니다. 저장본 부재 빈 상태 테스트와
구조 그룹이 모두 비어 있는 `NULLS` 케이스 테스트도 새 토글 동작에 맞춰 갱신됐습니다.
다만 뉴스·공시 카드의 기존 회귀 테스트 하나가 이번 변경으로 인해 함께 수정됐는데,
이는 아래 검증 포인트에서 다룹니다.

## 검증 포인트별 확인

- **기본 상태 리스트가 실제로 DOM에서 빠지는지** — `isBriefingExpanded`가 `false`일
  때 리스트 배열 삼항이 `null`을 반환해 `.map` 결과 자체가 렌더 트리에 들어가지 않고,
  `display: none` 같은 CSS 은닉이 아닙니다(`ResearchPage.tsx:1715-1743`). 새 테스트가
  `queryByText`로 세 그룹의 텍스트('매출 성장 지속' 등)가 `not.toBeInTheDocument()`임을
  확인해 스크린리더 접근성 관점에서도 실제로 제거됨을 보증합니다. body 문단은 반대로
  상시 DOM에 남고 `line-clamp-2` 클래스 유무만 바뀌는데, 이는 CSS 클램프 방식의 통상적
  구현이라 문제가 아닙니다.
- **토글 상태 전환** — `onClick`이 `setIsBriefingExpanded((isExpanded) =>
  !isExpanded)`로 함수형 업데이트를 쓰고 있어 상태 경쟁 없이 정확히 반전됩니다. 새
  테스트가 클릭 한 번에 펼침, 두 번째 클릭에 접힘까지 왕복 확인합니다.
- **접근성 속성 연결** — `aria-controls`가 가리키는 `research-briefing-content` id는
  클램프 문단과 리스트 블록을 함께 감싸는 `div`에 붙어 있어(`ResearchPage.tsx:1709`),
  접힘 상태에서도 그 `div` 자체는 항상 존재하므로 `aria-controls` 참조가 깨지지
  않습니다. `aria-expanded`는 boolean을 그대로 넘겨도 React가 DOM에는 문자열
  `"true"`/`"false"`로 직렬화하므로 정상 동작합니다. 버튼 라벨은 `aria-hidden`
  화살표가 접근성 트리에서 빠지므로 접근 가능한 이름이 정확히 '더 보기'/'접기'가
  되고, 테스트의 `getByRole('button', { name: '더 보기' })` 조회와 일치합니다.
- **저장본 부재·헤더 표시 회귀** — `EmptyState` + 생성 버튼 분기(`else` 블록)와
  `갱신 {createdAt}` 표시는 diff에 포함되지 않아 PR #220 구현이 그대로 유지됩니다.
  기존 "renders the empty briefing state and starts summary generation" 테스트가 이
  경로를 계속 커버합니다.
- **스코프 통제** — 프로덕션 코드 변경은 `ResearchPage.tsx` 한 파일, briefing 카드
  블록 안쪽으로 한정되어 있습니다. 핸드오프가 명시한 대로 새 공용 컴포넌트를 만들지
  않고 기존 토글 버튼 스타일을 재사용했고, 전문 별도 페이지 라우팅이나 BE 계약 변경은
  diff에 없습니다.
- **뉴스·공시 카드 테스트 수정의 성격** — `renders the news card without more toggle`
  류의 기존 테스트가 페이지 전역에서 `queryByRole('button', { name: '더 보기' })`가
  없음을 확인하던 방식에서, `newsCard` 섹션으로 범위를 좁혀 `within(newsCard).
  queryByRole('button')`이 없음을 확인하는 방식으로 바뀌었습니다. 이번 PR이 briefing
  카드에 실제 '더 보기' 버튼을 새로 추가했으므로 페이지 전역 조회는 이 버튼과
  충돌해 원래 테스트가 항상 실패하게 됩니다. 범위를 뉴스 카드 섹션으로 좁힌 수정은
  이 충돌을 피하기 위한 필수적인 후속 조치이고, 뉴스 카드 자체의 동작(링크만 있고
  버튼 없음)은 그대로 검증되므로 스코프 이탈이 아니라 정확한 수정입니다.
- **body가 짧아 clamp가 안 걸리는 경우** — 핸드오프 Requirements 4번 항목이지만
  Test Requirements 4종에는 별도로 명시되지 않았습니다. `keeps the briefing paragraph
  when every structured group is empty` 테스트(`NULLS` 라우트, body가 '기존 브리핑
  문단만 표시합니다.'로 짧음)가 이 케이스에서도 클램프 클래스가 정상 적용/해제되고
  리스트 없이도 렌더가 깨지지 않음을 간접적으로 확인합니다. `line-clamp-2`는 텍스트가
  2줄 미만이면 자연히 아무 효과가 없는 CSS 유틸이라 별도 시각 테스트가 없어도 위험이
  낮습니다.
- **Test Requirements 4종 대응** — 기본 상태 리스트 없음(`queryByText`), 토글 후
  리스트 등장(`findByText`), 빈 상태 유지, 기존 briefing 관련 회귀 테스트가 모두
  갱신된 테스트로 실제 대응됩니다.

## Final Recommendation

**Blocking 없음 — 머지 가능.** 리스트 3종은 조건부 렌더로 실제 DOM에서 빠지고
body는 CSS 클램프로 처리되어 각 방식이 목적에 맞게 선택됐습니다. `aria-controls`·
`aria-expanded`·버튼 접근 가능한 이름이 모두 정확하고, 저장본 부재 빈 상태·헤더
표시 등 PR #220 구현은 diff 범위 밖이라 회귀가 없습니다. 뉴스·공시 카드 테스트
수정은 새 버튼과의 이름 충돌을 피하기 위한 필수적인 조정이며 스코프 이탈이 아닙니다.
핸드오프 Test Requirements 4종이 모두 실제 테스트로 대응되고, CI와 로컬 재실행
(format/typecheck/lint/test)이 모두 그린입니다.
