## 판정: **조건부 머지 가능**

Blocking 항목 1개가 있다. API 경로 prefix 누락이 실제 운영 환경에서 404를 유발한다. 수정 방법이 단순하여 fix 후 재검증 없이 머지 가능하다.

## Blocking 발견 사항

### B-1 API 경로 prefix 누락 — `src/shared/api/hooks/` 전체

**심각도**: Blocking

**위치**: `useDashboardSummary.ts` L13, `useWatchlists.ts` L11, `useWatchlistItems.ts` L15, `usePortfolios.ts` L11, `usePortfolioSummary.ts` L14

기존 `src/shared/auth/authApi.ts`와 `src/shared/api/client.ts`의 경로 규약을 확인하면:

```ts
// authApi.ts L25 — 기존 규약
await apiPost<LoginDto>('/auth/login', ...)
// authApi.ts L44
await apiGet<MeUser>('/auth/me')
// client.ts L29 — refresh 예시
await fetch(`${baseUrl}/auth/refresh`, ...)
```

`apiGet`/`apiPost`에 전달하는 경로는 `VITE_API_BASE_URL` 바로 뒤에 붙는다. `frontend-api-spec.md`의 실제 API 경로는 모두 `/api/v1/...` 형태인데(`GET /api/v1/dashboard/summary`, `GET /api/v1/watchlists` 등), 신규 훅들은 `/api/v1` prefix를 생략하고 있다.

```ts
// useDashboardSummary.ts — 현재 (잘못됨)
await apiGet<DashboardSummaryDto>('/dashboard/summary')

// 올바른 경로
await apiGet<DashboardSummaryDto>('/api/v1/dashboard/summary')
```

기존 auth 경로가 `/auth/login`(prefix 없음)인 것은 백엔드 라우터 구성에서 auth만 `/api/v1`이 아닌 루트에 마운트되기 때문이다(`POST /api/v1/auth/login`이 실제 spec에 명시). 그러나 신규 비즈니스 API는 예외 없이 `/api/v1` prefix가 필요하다. 로컬 개발 중 프록시 설정으로 가려지더라도 스테이징·운영에서 404가 발생한다.

**수정**: 5개 훅의 경로를 `/api/v1/dashboard/summary`, `/api/v1/watchlists`, `/api/v1/watchlists/{id}/items`, `/api/v1/portfolios`, `/api/v1/portfolios/{id}/summary`로 변경한다.

## 양호 확인 사항

### G-1 갭 처리 정확성 — 설계기록 갭 표와 완전히 일치

BE 출처 없는 필드에 더미값을 삽입하지 않았고, 처리 방침을 정확히 따랐다.

- **Dashboard**: `*_delta` 4개가 항상 `null`이므로 어댑터에서 `''`로 변환, 컴포넌트에서 `delta ? <span>...</span> : null`로 조건부 렌더한다. `cash_weight: null` → `cashRatio: null` → `value == null ? '—' : formatMetricValue(...)`. 핸드오프 요구사항과 정확히 일치한다.
- **Watchlist**: PER, PEG, 상태, newsRisk, valuation, themeHeat, aiVerdict, Sparkline 열을 모두 제거했다. 테이블 헤더는 `['', '종목', '변화(1D)', '마지막 갱신', '']`만 남겨 설계기록 §4 방침 준수. 시장 필터와 위험 필터 드롭다운을 `disabled` 처리했다. `summaryCards` 나머지 3개는 `'—'`를 값으로 쓰되 `deltaLabel: ''`로 고정.
- **Portfolio**: `dayChangeValue`/`dayChangePercent` 기반 SummaryCard 제거, 3-card 레이아웃으로 축소. "일간 손익" 카드 완전 제거 확인(`screen.queryByText('일간 손익')`으로 테스트도 검증). 보유 종목 테이블에서 섹터·일간 변화 열 제거 확인. 종목명 대신 `symbol: String(position.asset_id)`, 서브텍스트에 `asset_id {holding.assetId}` 표시 — 임의 종목명 삽입 없음.

### G-2 어댑터 변환 정확성

`parseDecimal`을 사용한 문자열 Decimal 변환이 올바르게 적용됐다.

- `cash_weight: "0.18"` → `parseDecimal * 100 = 18` (cashRatio 퍼센트)
- `position.weight: "0.951..."` → `decimalOrZero * 100 ≈ 95.1` (보유 비중 퍼센트)
- `sector_weights[].weight` 동일 패턴
- `expand=asset` 없는 item: `dtos.filter((dto) => dto.asset)`으로 skip — 방어 처리 올바름
- `decimalOrZero` 헬퍼 함수로 `null`/`undefined` 입력을 `0`으로 처리

하나 주의할 점: `decimalOrZero`가 `cash_weight: null`을 `0`으로 변환하는데, `PortfolioSummaryDto`에서 `cash_weight`는 nullable로 선언되지 않았다(`cash_weight: string`). BE spec상 필드가 누락될 수 없으므로 현재 코드는 안전하다. 단, 향후 BE가 null을 반환하는 경우를 위해 DTO 타입에 `string | null`을 명시하는 것이 더 정확하다. 이번 리뷰에서는 Blocking으로 처리하지 않는다.

### G-3 상태 처리 — 로딩·에러·빈 목록 모두 처리

세 화면 공통으로 `isPending → <Skeleton>`, `isError → <ErrorState onRetry>`, 빈 목록 → `<EmptyState>` 패턴이 일관되게 구현됐다.

- `WatchlistPage`의 `isError` 분기에서 두 쿼리의 에러를 `??` 연산자로 병합해 첫 번째 에러 메시지를 표시한다.
- Watchlist·Portfolio는 `isPending` 체크를 컴포넌트 전체 로딩 후에 처리하는데, 두 번째 쿼리가 `enabled: false`일 때도 `isPending`이 `true`가 될 수 있다는 점에 주의한다. 현재 TanStack Query v5에서 `enabled: false`인 쿼리의 초기 상태는 `isPending: true`이므로 `selectedWatchlistId == null`이면 아이템 쿼리는 `isPending = true`로 유지된다. 이 경우 Skeleton이 표시되다가 watchlists 쿼리 완료 후 `selectedWatchlistId`가 채워지면 items 쿼리가 시작되는 흐름이라 UX상 자연스럽게 작동한다. 단, watchlists가 빈 배열을 반환하면 items 쿼리는 영원히 `isPending = true`인 채로 남는다.

  **보완 권장**: Watchlist 빈 목록 분기를 `itemsQuery.isPending` 체크 앞으로 이동하거나, `!selectedWatchlistId` 시 items 쿼리의 `isPending`을 포함하지 않도록 조건부 처리한다. 이번 리뷰에서는 Blocking으로 처리하지 않되 후속 이슈에서 개선을 권장한다.

## 오케스트레이터 정정 (Opus, 최종 검증)

이 리뷰는 Sonnet/VFF가 작성했다. 최종 검증에서 **B-1의 진단 방향이 틀렸음**을 정정한다.

- **실제 경로 규약**: `VITE_API_BASE_URL`이 `/api/v1`을 **포함**한다. 근거: 기존 머지된
  인증 흐름(PR #52)이 `authApi.ts`에서 `/auth/login`·`/auth/me`를, client가 `/auth/refresh`를
  **prefix 없이** 호출하는데, 이들이 BE의 실제 라우트 `POST /api/v1/auth/login` 등에 도달하려면
  base가 반드시 `…/api/v1`이어야 한다. 따라서 **모든 신규 경로도 `/api/v1`을 생략**해야 한다.
- VFF 리뷰의 "auth만 루트(`/api/v1` 아님)에 마운트된다"는 근거는 spec(`POST /api/v1/auth/login`)과
  **모순**된다. VFF 권고대로 `/api/v1`을 추가하면 `…/api/v1/api/v1/dashboard/summary`로
  **더블 프리픽스 404**가 발생한다.
- **현재 코드 상태**: 신규 훅 5개는 이미 `/api/v1`을 **제거한 상태**(authApi 규약과 일치)이며
  이것이 **정답**이다. 즉 B-1이 지적한 위치는 옳았으나(불일치 존재) **수정 방향은 반대**였고,
  올바른 수정(접두사 제거)은 최종 검증 단계에서 이미 적용·재검증 완료(typecheck·test·format 통과).
- VFF의 R-1(빈 watchlist에서 items 쿼리 `isPending` 잔류)은 **유효한 지적**으로 후속 처리 대상.
  G-1~G-6의 갭 처리·어댑터·테스트·스코프 평가는 정확하다.

**최종 판정: 머지 가능**(경로는 authApi 규약대로 prefix 없음이 정답, 이미 반영됨).
