**계약 일치**: BE `project_stock#299`의 `app/domains/research_summary/schema.py`를
직접 대조했습니다. `CounterPoint`는 `id`·`claim`·`basis`·`basis_type`(`CounterBasisType`:
VALUATION/FUNDAMENTALS/COMPETITION/MACRO/SENTIMENT)·`strength`(`CounterPointStrength`:
WEAK/MODERATE/STRONG, 필수)·`source_label`(`str | None = None`)로 정의되어 있고,
FE `CounterPointDto`(`dto.ts` 26-38행)가 필드명·enum 값(대문자 문자열)·nullable 여부까지
정확히 일치합니다. `ResearchSummaryResponse.counter_points`는
`Field(default_factory=list)`라 실제로는 절대 `null`을 내려주지 않고 항상 최소 `[]`이지만,
FE dto는 `counter_points?: CounterPointDto[] | null`로 더 방어적으로 잡아 두었습니다.
BE가 언젠가 nullable로 바뀌어도 깨지지 않는 여유이므로 문제로 보지 않았고, Questions에
확인 차원으로 남겼습니다.

**미지 값·fallback 경로**: `adapters.ts`의 `normalizeCounterPointStrength`는
WEAK/MODERATE/STRONG 외 값이면 `null`을 반환하고, `basisTypeLabel` 매핑도 사전에 없는
`basis_type`이면 원문 문자열을 그대로 씁니다(`counterPointBasisTypeLabels[point.basis_type]
?? point.basis_type`). `adapters.test.ts`가 다섯 가지 정상 매핑 전부와, 미지 `basis_type`
(`REGULATION` 원문 유지)·미지 `strength`(`VERY_STRONG` → `null`)를 각각 테스트로
커버합니다. fallback 경로 세 가지(`counter_points` 있음 / 없고 `counter_view`만 있음 /
둘 다 없음)는 `ResearchPage.test.tsx`의 `NULLS`·`MSFT` 픽스처로 각각 검증되어, 설계
문서 5절이 요구한 동작과 diff가 정확히 일치합니다.

**강도 배지 톤**: `CounterPointStrengthBadge`는 STRONG→`riskLevel="높음"`,
MODERATE→`riskLevel="중간"`(둘 다 `status-level-*` 톤), WEAK→`tone="neutral"`로
분기합니다. `Badge` 컴포넌트(`src/shared/ui/Badge.tsx`, `stockStatus.ts`)를 직접 확인한
결과 이 매핑은 설계 문서 4절("STRONG=status-level-high 톤, MODERATE=status-level-medium
톤, WEAK=neutral 톤")과 정확히 일치합니다.

## Suggestions

**S1: 행별 독립 그리드라 근거 유형 배지 폭에 따라 주장 텍스트 시작 위치가 행마다 달라집니다.**
`CounterViewPanel`의 각 `<li>`는 `grid grid-cols-[auto_auto_minmax(0,1fr)]`로 자기
자신만의 그리드 컨테이너입니다. CSS Grid는 서브그리드를 쓰지 않는 한 형제 요소끼리
컬럼 폭을 공유하지 않으므로, `auto`로 잡힌 1·2번째 컬럼(강도 배지·근거 유형 배지)의
폭은 행마다 자신의 콘텐츠에만 맞춰 계산됩니다. 실제로 `ResearchPage.test.tsx`의 데모
데이터만 봐도 근거 유형 라벨 길이가 "밸류에이션"(5자)부터 "심리"(2자)까지 다양해서,
3번째 컬럼(주장 텍스트)의 시작 x좌표가 행마다 어긋납니다. `strength`가 `null`이라
배지가 생략된 행에서 근거 유형 배지에 `col-start-2`를 강제하는 처리도 같은 근본
원인(행별 독립 그리드) 때문에 정렬을 완전히 복구하지 못합니다. 참고로 리스크
패널(`RiskPanel`)은 같은 행 목록 구조를 쓰지만 컬럼을 고정폭(`0.5rem`,
`minmax(0,9rem)`)으로 잡아 이 문제가 없습니다. 데이터는 정확히 렌더되고 테스트도
모두 통과하므로 기능적 결함은 아니지만, 설계 문서가 명시한 "리스크 패널과 같은 행
정렬" 목표를 시각적으로 완전히 달성하지 못하는 지점이라 블로킹으로는 보지 않고
후속 폴리시(고정폭 또는 `min-w` 지정)로 남깁니다.

## Questions

**Q1: `counter_points`를 nullable로 잡은 방어적 여유가 의도적인지 확인 부탁드립니다.**
BE `ResearchSummaryResponse.counter_points`는 `default_factory=list`라 응답에서 절대
`null`이 오지 않고 항상 최소 `[]`입니다. FE `ResearchSummaryDto.counter_points`는
`CounterPointDto[] | null`로 더 넓게 잡혀 있는데, 이것이 향후 BE 계약이 nullable로
바뀔 가능성에 대비한 의도적 여유인지, 아니면 다른 optional 필드들과의 스타일 일관성
때문인지 확인 차원의 질문입니다. 어느 쪽이든 현재 동작에는 영향이 없어 블로킹은
아닙니다.

**Q2: 구계약 `counter_view` 불릿 경로를 걷어낼 후속 이슈가 이미 추적되고 있는지 궁금합니다.**
설계 문서 2절에 "counter_view 제거는 BE 후속 이슈 이후"로 명시되어 있는데, BE가
`project_stock#299`를 배포한 뒤 이 fallback 경로와 `counterView`/`CounterViewPanel`의
이중 분기를 정리할 이슈가 별도로 등록돼 있는지 확인 부탁드립니다. 없다면 데드 코드로
남을 위험이 있어 에픽 #152 후속 작업으로 등록해 두는 편이 좋겠습니다.

## Final Recommendation

Blocking이 없습니다. 머지 가능 판단입니다.

BE `project_stock#299` 계약과 FE `CounterPointDto`가 필드명·enum 값·nullable 여부까지
정확히 일치하고, 실계약 픽스처 규율에 맞춰 테스트 데이터도 대문자 enum 문자열을
그대로 사용합니다. 미지 `basis_type`·`strength` 처리와 fallback 세 경로(구조화 데이터
있음 / 구계약 불릿만 있음 / 둘 다 없음)가 모두 테스트로 커버됩니다. CI(`Verify React
Template`)는 `pass`이고, 로컬 4종 검증(format:check·typecheck·lint·test 511개)도 모두
통과했습니다. 그리드 행 정렬 관련 제안 한 건과 확인 차원의 질문 두 건을 남겼지만
어느 것도 병합을 막을 사유는 아닙니다.

최종 머지 권한은 개발자에게 있습니다.

## Resolution

- S1 — 반영했습니다. 행 그리드를 `grid-cols-[3.25rem_6rem_minmax(0,1fr)]`
  고정 폭 컬럼으로 바꾸고 강도·유형 배지에 `justify-self-start`를 적용해,
  라벨 길이와 무관하게 모든 행에서 배지와 주장 텍스트의 시작 위치가
  정렬되도록 했습니다.
- Q1 — 의도적입니다. dto를 nullable로 넓게 잡은 것은 구버전 BE(필드 부재)
  응답까지 경계에서 방어하기 위한 것으로, adapters에서 빈 배열로 정규화해
  내부 타입은 non-null을 유지합니다.
- Q2 — 등록되어 있습니다. BE의 `counter_view` 제거 후속 이슈는
  project_stock#300이며, FE fallback 제거는 해당 이슈 처리 시 함께
  다룹니다.
