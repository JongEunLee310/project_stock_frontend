# PR #301 로컬 리뷰 — 예상 자금 흐름을 BE 수치 구간 계약에 연결 (#298)

## Review Summary

BE가 지운 필드를 FE가 계속 읽고 있어 화면이 조용히 비어 있던 결함을 고치는 PR입니다. 단일
구현 커밋(`fix: 자금 흐름 수치 구간을 표시한다`)이며 `src/features/news-insights/` 네 파일만
건드립니다. diff는 115줄 추가·8줄 삭제이고 그중 61줄이 어댑터 테스트입니다.

**결함의 성격이 이번 작업의 전제입니다.** BE #393(PR `project_stock#395`, dev 머지 완료)이
ADR-017에 따라 문자열 라벨 `estimated_range`를 지우고 수치 구간 `estimated_flow`로 교체했는데,
FE `dto.ts`는 옛 필드를 그대로 선언하고 있었습니다. 마이그레이션에서 컬럼 자체가 제거돼 응답에
없는 필드이므로 값은 항상 `undefined`가 되고, 패널은 모든 섹터를 `범위 미제공`으로 떨어뜨립니다.
**타입 검사도 테스트도 이 상태를 통과합니다** — DTO는 와이어를 선언할 뿐 실제 응답과 대조하지
않기 때문입니다. 화면에서 값이 비어 있는 것을 눈으로 보기 전에는 드러나지 않는 종류입니다.

**표현 파일을 한 줄도 건드리지 않는 것이 이번 PR의 제약입니다.** 프론트엔드 표현은 현재 사용자가
직접 다듬는 중이라 동결 상태입니다. 뷰 필드 이름 `estimatedRange`와 타입 `string | null`을 그대로
두고 **값을 만들어 오는 자리만** 바꾸면 위젯이 참조하는 코드가 바뀌지 않고, 위젯·페이지 테스트의
픽스처도 뷰 레벨 문자열이라 무수정으로 통과합니다.

수정은 두 갈래입니다. `dto.ts`에서 와이어 타입을 `estimated_flow`로 교체하고 구간 모양을
`EstimatedFlowDto`로 뽑았습니다. `adapters.ts`에는 `formatEstimatedFlow`를 두어 구간을 파싱하고
표시 문자열 또는 `null`을 반환합니다.

이번 리뷰는 보호 경로가 정말 무변경인지, 표시 규칙의 경계값, 값을 지어내지 않는지, 같은 유형의
결함이 다른 곳에 더 있는지를 축으로 봤습니다.

## Suggestions

**S1. 원시 수치를 뷰에 남기지 않는다 — 의도된 제약, #294의 선행 비용.** 표시 문자열만 담으므로
이후 막대 길이를 값에 비례시킬 때(#294) 어댑터에서 다시 파싱해야 합니다. 원시 수치를 함께 담는
편이 그때 편하지만, 그러려면 뷰 필드의 모양이 바뀌고 위젯 참조도 따라 바뀝니다. 표현 동결이
우선이므로 지금은 담지 않는 편이 맞습니다. #294가 표현을 다시 여는 시점에 함께 정리하면 됩니다.

**S2. 억 단위로 줄이면 서로 다른 두 값이 같은 라벨이 될 수 있다 — 실사용에서 닿지 않음.**
`low`와 `high`가 같은지는 **줄이기 전 원시 값**으로 판단하고 라벨은 줄인 뒤 만듭니다. 그래서
억 단위 소수 첫째 자리에서 구분되지 않는 두 값은 `1~1억원`처럼 표시됩니다. 자금 흐름 전망에서
그만큼 좁은 구간이 나올 일은 없습니다.

**S3. 원 단위 표시에 소수가 붙을 수 있다 — 실사용에서 발생하지 않음.** 억 미만 분기는
`formatMoney`에 옵션을 넘기지 않아 `ko-KR` 기본값(소수 3자리까지)을 씁니다. BE가 금액을
`Numeric(20,4)`로 저장하므로 이론상 `123.456원`이 가능하지만, 이 지표의 단위가 억 이상이라 닿지
않는 경로입니다.

**S4. `aggregation_windows`·`expected_net_flow`는 이번에도 소비하지 않는다 — 의도된 범위
제한.** BE가 #390·#393에서 함께 추가한 두 필드는 표시할 자리가 없어 DTO 선언조차 하지
않았습니다. 소비하지 않는 선언은 죽은 코드이고, 자리를 만드는 일은 시각화 정합(#294)의 몫입니다.

## Questions

**Q1. 보호 경로가 정말 무변경인가.** 확인해 해소했습니다. `git diff --stat origin/main...HEAD --
src/widgets/ src/pages/` 출력이 비어 있습니다. 변경된 네 파일은 모두
`src/features/news-insights/` 아래입니다. 위젯·페이지 테스트는 손대지 않았고 그대로
통과합니다 — 뷰 필드의 이름과 타입이 유지됐다는 증거이기도 합니다.

**Q2. 표시 규칙의 경계에서 값이 깨지지 않는가.** 확인해 해소했습니다. 어댑터 테스트가 억 이상,
억 미만, 음수를 포함한 구간, 비-KRW 통화(공백·소문자 포함), `low === high`, 통화가 빈 문자열,
`null`, 숫자로 읽히지 않는 값, 유한하지 않은 값 여덟 가지를 덮습니다. 음수 부호가
보존되고(`-2.5~1.5억원`), 통화가 비면 `KRW`로 떨어지며, 두 값이 같으면 `~`로 잇지 않습니다.

**Q3. 값을 지어내지 않는가.** 확인해 해소했습니다. 구간이 `null`이거나 `low`·`high`를 유한한
수로 읽을 수 없으면 `null`을 반환하고 화면은 `범위 미제공`을 유지합니다. `Number.isFinite`
가드가 있어 `'Infinity'` 같은 문자열도 걸립니다 — `parseDecimal`은 `Number()` 기반이라 `NaN`
검사만으로는 통과하는 값입니다.

**Q4. 같은 유형의 결함이 다른 곳에도 있는가.** 구현자가 전수 확인해 추가 발견이 없다고
보고했고, 리뷰에서 `dto.ts`를 다시 훑어 BE 응답에 없는 필드 선언이 남아 있지 않음을
확인했습니다. 다만 **이 결함 유형은 다시 발생합니다.** DTO와 실제 응답을 대조하는 장치가 없는
한, BE가 필드를 지울 때마다 FE는 조용히 빈 값을 표시합니다. 계약 픽스처를 BE 응답에서 생성하는
방식이 근본 해법이지만 이번 범위 밖이며, 별도 판단이 필요한 사안으로 남깁니다.

## Final Recommendation

머지 가능합니다. 핸드오프의 요구를 항목별로 확인했습니다. 응답에 없는 필드 참조가 0건 남았고,
표시 규칙의 경계 여덟 가지가 테스트로 덮이며, 구간이 없을 때 대체 숫자를 만드는 경로가
없습니다.

범위는 지켜졌습니다. 변경은 `src/features/news-insights/` 네 파일뿐이고, **`src/widgets/`와
`src/pages/`는 소스도 테스트도 무변경**입니다. 소비할 자리가 없는
`expected_net_flow`·`aggregation_windows`는 DTO 선언조차 하지 않아 죽은 코드가 생기지
않았습니다. Protected Files는 위 두 경로이며 보존됐습니다.

테스트는 실제 시드값(`800000000000.0000`~`1800000000000.0000`, `KRW`)을 픽스처로 쓰고 표시
문자열이 `8,000~18,000억원`이 되는 것을 단언합니다. 지어낸 값이 아닙니다. 위젯·페이지 테스트가
무수정으로 통과한다는 사실 자체가 표현이 그대로임을 보여 줍니다.

Blocking은 없습니다. S1은 표현 동결을 우선한 데 따른 의도된 제약이고, S2·S3은 실사용에서 닿지
않는 표시상의 경계이며, S4는 의도된 범위 제한입니다. Q1·Q2·Q3은 확인해 해소했고, Q4는 재발
방지 장치가 별도 판단 사안으로 남습니다.

최종 머지 권한은 개발자에게 있습니다.
