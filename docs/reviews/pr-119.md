리뷰어: Claude Code (Sonnet / Value-for-Fable). 구현: Codex (GPT-5, medium). 브랜치: feat/117-watchlist-phase2 → main. 관련: FE #117, 설계 docs/designs/117-watchlist-phase2.md, 핸드오프 .codex/tasks/task-045-watchlist-phase2.md.

## Review Summary

설계 §1–§6의 결정 사항을 전부 구현했으며, BE PR #235로 확정된 계약 리터럴과의 정합성도 확인됩니다.

주요 변경 내용은 다음과 같습니다. `resolveStatusBadge`가 BE의 7개 status 값을 안정/관망/위험 증가 3단계로 접어 반환하며, `adapters.ts`에 단일 함수로 집중되어 있습니다. 위험 필터 드롭다운은 시장 필터와 독립적으로 AND 결합되고, 두 필터 모두 변경 시 page를 1로 초기화합니다. `추가일` 컬럼은 `마지막 갱신`(`asset.reference_at`)으로 교체되었고, 관련 `SortKey`·`sortLabels`·`sortWatchlistRows` 분기도 함께 정리되었습니다. `useWatchlistSparklines`는 첫 번째 관심목록 ID를 내부 API 호출로 조회한 뒤 `/watchlists/{id}/sparklines?range={range}`를 호출해 `symbol → number[]` 맵을 반환하며, staleTime 5분으로 페이지 이동 시 재조회를 억제합니다. 요약 카드의 전일 대비 델타는 기존 `useWatchlistSummaryTrends` 데이터를 그대로 활용해 BE 변경 없이 구현됩니다.

PR #118 리뷰 논블로커 3건도 모두 반영됩니다. `FloatingMarketCard` wrapper `<aside>`에서 `aria-label`이 제거되었고(S1), 관심 해제 mutation pending 상태가 `removingItemId === stock.id`로 행 단위로 국한되었으며(S2), 시장 필터 변경 시 `setPage(1)`이 추가되었습니다(S4).

BE 계약 리터럴 검증 결과, `app/domains/signals/types.py`의 `SignalType` enum 및 `WATCHLIST_STATUS_NORMAL` 상수가 모두 대문자 문자열임을 실측으로 확인했습니다. 테스트 픽스처에도 `// app/domains/signals/types.py:4-13` 출처 주석이 기재되어 있습니다.

## Suggestions

**S1 · `resolveStatusBadge` 이중 호출 (비차단, 경미한 중복)**

`visibleStocks` 메모와 행 렌더링 양쪽에서 `resolveStatusBadge(stock.status)`를 각각 호출합니다. 함수 자체가 순수하고 단순해 현 규모에서 체감 비용은 없지만, `WatchlistAssetRow`에 `statusLabel: string` 파생 필드를 두거나 `adaptWatchlistAsset` 단계에서 미리 계산해 두면 두 호출 지점이 단일 출처를 참조하게 됩니다. 현재 범위 내에서 허용되며, 파생 필드 추가는 Phase 3 이전 리팩터링 기회에 검토할 수 있습니다.

**S2 · `useWatchlistSparklines` 내부 watchlist 목록 이중 조회 (비차단, 설계 범위 내)**

`useWatchlistSparklines`의 `queryFn`이 `/watchlists?page=1&size=20`를 내부적으로 한 번 더 호출해 첫 번째 관심목록 ID를 확보합니다. 이 호출은 `useWatchlistAssets` 캐시와 독립적이어서 최초 로드 시 추가 네트워크 왕복이 발생합니다. 설계 §4에서 스파크라인을 items 쿼리와 독립된 생명주기로 관리하도록 결정했으므로 현 구현은 설계 의도에 부합합니다. 추후 `enabled: !!firstWatchlistId` 패턴과 별도 watchlist 목록 쿼리를 결합하면 중복 호출을 제거할 수 있습니다.

**S3 · `reference_at: null → '—'` 검증이 번들 테스트에 통합됨 (비차단, 테스트 명시성)**

핸드오프 §Test Requirements는 `reference_at` null 행의 `마지막 갱신` 셀에서 `—` 렌더링을 확인하는 별도 테스트를 지정했습니다. 구현은 `expect(within(table).getAllByText('—').length).toBeGreaterThan(0)`로 메인 렌더 테스트에 통합해 처리했습니다. TSLA 픽스처의 `referenceAt: null`이 이 assertion을 통과시키므로 기능 커버리지는 확보되어 있으나, `—`의 출처(마지막 갱신 셀인지 스파크라인 셀인지)가 테스트 의도상 모호합니다. 별도 케이스로 분리하면 의도가 더 명확해집니다. 현재 커버리지 수준에서 블로커는 아닙니다.
