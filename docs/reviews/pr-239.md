# PR #239 로컬 리뷰 — feat: /alerts를 관제 전용으로 축소 — 규칙·채널 제거 및 설정 링크 (#234)

## Review Summary

ADR-014를 FE에 적용하는 3단계 중 2단계입니다. 커밋은 두 건이며 핸드오프 문서
(`.codex/tasks/task-091-alerts-monitoring-only.md`) 추가와 구현으로 나뉩니다.

1단계(#233, PR #237)에서 규칙과 채널이 `/settings`로 옮겨졌으므로, 이번에는 `/alerts`에서
같은 기능을 걷어냅니다. 제거가 중심인 변경이며 `src/pages/ui/AlertsPage.tsx`는 131행이
줄고 그만큼 단순해졌습니다. `AlertRuleTable`·`AlertRuleBuilder`·`NotificationChannelPanel`
렌더링과 `BuilderState` 상태, create·edit·duplicate 핸들러, `useSearchParams` 기반 쿼리
처리, "새 규칙 만들기" 버튼이 모두 빠졌습니다. 남은 것은 `AlertSummaryCards`와
`AlertHistoryPanel`·`AlertDetail`이며, 설정 영역과 결과 영역을 가르던 강조 구분선도 함께
정리됐습니다.

새로 들어온 것은 두 가지입니다. 헤더 오른쪽의 `/settings` 링크("알림 규칙 설정")는
`appRoutePaths.settings`를 참조해 경로 하드코딩을 피했습니다. 그리고 규칙이 하나도 없을 때
설정으로 유도하는 안내를 `EmptyState`로 표시하는데, 판단 근거는 `useAlertOverview`의
`activeRuleCount + pausedRuleCount === 0`입니다. 핸드오프에서 신규 API 호출을 금지했고
기존 조회를 재사용하도록 요구했는데 그대로 지켜졌습니다.

리뷰는 세 축으로 봤습니다. 제거 과정에서 관제 기능이 온전히 남았는지, 설정으로 가는 경로가
사용자에게 닿는지, 그리고 #235 이전의 중간 상태가 사용자에게 어떻게 보이는지입니다.

## Blocking

None.

## Suggestions

**S1. deep-link가 이번 단계에서 아무 동작도 하지 않습니다 — 의도된 중간 상태이나 #235를
바로 이어야 합니다.** Signals 카드의 "이 시그널 변화 알림 받기"는 여전히
`/alerts?builder=create&symbol=`로 이동하는데, 쿼리를 소비하던 `useSearchParams` 처리가
`/settings`로 옮겨간 뒤 이번 PR에서 `/alerts`의 잔여 처리까지 제거됐습니다. 그래서 지금
버튼을 누르면 `/alerts`에 도착만 하고 Rule Builder가 열리지 않습니다. 핸드오프와 이슈
#234의 비포함에 명시된 계획된 구간이고 3단계 #235가 목적지를 `/settings`로 바꾸면
해소되지만, 그 사이에 배포되면 사용자에게는 버튼이 고장 난 것으로 보입니다. 병합을 막지는
않되 #235를 연달아 처리하는 편이 좋습니다.

**S2. 빈 상태 판단이 overview 로딩 중에는 성립하지 않습니다 — 올바른 보수적 처리입니다.**
`hasNoRules`는 `overview !== undefined`를 함께 요구하므로 로딩 중이나 조회 실패 시에는
안내가 뜨지 않습니다. 규칙이 있는데도 "규칙이 없습니다"를 잠깐 보여주는 것보다 낫고, 조회가
실패하면 `AlertSummaryCards`가 자체 에러 표시를 담당합니다. 현재 구조에서 적절합니다.

## Questions

**Q1. 헤더 링크와 빈 상태 안내가 모두 설정으로 향하는데 중복인지 확인했습니다.** 리뷰 중
확인한 결과 두 진입점은 역할이 다릅니다. 헤더 링크는 규칙이 있는 사용자가 편집하러 가는
상시 경로이고, 빈 상태 안내는 규칙이 없어 관제할 대상 자체가 없는 사용자를 위한 안내입니다.
빈 상태는 조건부로만 나타나므로 화면에 두 버튼이 동시에 보이는 경우는 규칙이 0인 상황
하나뿐이며, 그때는 안내가 더 눈에 띄는 편이 낫다고 판단합니다. 병합 판단에 영향은
없습니다.

## Final Recommendation

병합 가능합니다. 다만 S1 때문에 #235와 연달아 머지하기를 권합니다.

이슈 #234의 완료 조건을 항목별로 확인했습니다. `/alerts`에 규칙 테이블·Rule Builder·채널
설정이 남아 있지 않고(테스트 `renders monitoring sections and removes rule, builder, and
channel settings`), 관제 요약과 발생 내역이 화면 위쪽에 오며, 설정 링크가
`appRoutePaths.settings`로 이동하고(`links to alert settings through the configured
route`), 규칙이 없을 때 유도 안내가 보입니다(`guides users to settings when there are no
active or paused rules`). 알림 상세 열람도 별도 테스트로 남았습니다.

범위가 지켜졌습니다. 변경 파일은 `AlertsPage.tsx`와 그 테스트, 핸드오프 문서 세 건뿐입니다.
Protected Files로 지정한 `SettingsPage.tsx`와 `navigation.ts`, 위젯 내부 구현은 diff에
없습니다. 신규 API 호출도 추가되지 않았습니다.

회귀 위험은 낮다고 봅니다. 제거된 기능은 이미 `/settings`에서 동작하므로 사용자가 잃는
기능이 없고, 남은 관제 경로는 위젯을 그대로 쓰기 때문입니다.

테스트는 단순 삭제가 아니라 교체됐습니다. 제거된 요소를 전제하던 세 건(통합 순서, deep-link
prefill, 쿼리 없는 진입)이 빠지고 제거 확인·설정 링크·빈 상태 유도·상세 열람 네 건이
들어와 순증했습니다.

Blocking은 없습니다. Suggestions S1은 #235로 해소되는 계획된 중간 상태이고 S2는 확인
사항이며 Questions Q1은 리뷰 중 해소했으므로, 셋 다 병합을 막지 않습니다.

최종 머지 권한은 개발자에게 있습니다.
