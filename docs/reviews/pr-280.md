# PR #280 로컬 리뷰 — 인사이트 설명·반대 관점 패널 (#268)

## Review Summary

토픽 상세 "왜 이런 인사이트가 나왔나"(§5.10) placeholder를 실데이터로 교체하고 반대 관점 패널(§5.11)을 `/explanation`의 구조화된 counter_view로 확장한 PR입니다. 단일 커밋(`뉴스 인사이트 설명과 반대 관점 패널 구현`)입니다.

`src/features/news-insights/`에 explanation dto·adapter(`adaptNewsTopicExplanation`)·query(`useNewsTopicExplanationQuery(topicId)`, `enabled` 가드)를 추가했습니다. `InsightExplanationPanel`과 확장된 `CounterViewPanel`이 이 하나의 query를 공유합니다.

**Part A — 인사이트 설명(#268, 스펙 §5.10).** `InsightExplanationPanel`은 기여 요인 비율을 `factor.contributionRatio`(BE 산출값)로 막대 렌더하며 FE에서 생성·재계산하지 않습니다. 막대에 라벨+%를 병기하고 `aria-valuenow`로 접근성을 확보했으며, 메타(분석 버전·데이터 범위·마지막 갱신·누락 데이터·반대 근거 수·신뢰도·한계)와 "AI 분석·신뢰도" 배지로 분석 출처를 표시합니다. 토픽 상세 `plannedPanels.explanation`을 대체했습니다.

**Part B — 반대 관점 확장(#268, 스펙 §5.11).** `CounterViewPanel`을 확장해 1차 `/topics/{id}`의 `counterArguments`를 base로 항상 유지하고, `/explanation` counter_view의 무효화 조건·선반영 가능성(already_priced_in)·CONTRADICTING evidence를 추가 섹션으로 붙입니다. explanation이 로딩·오류(미분석 토픽 500)면 `ExplanationUnavailable`이 "기본 반대 관점은 계속 확인할 수 있습니다"로 graceful 처리해 base 반대 근거 가시성을 보존합니다.

페이지는 두 패널에 `explanationQuery`를 연결하고, base counter_arguments는 `detailQuery`에서 유지하며, `actionChecklist` placeholder는 #270 소관이라 issue 라벨만 정정하고 유지했습니다. 두 패널은 독립적으로 부분 실패를 격리합니다.

이번 리뷰는 기여 비율의 BE 값 렌더(FE 생성 금지), 반대 관점 base 유지 + 확장 graceful, 미분석 토픽 500 격리, 사실/분석 구분, 기존 CounterViewPanel 확장에 따른 회귀를 축으로 봤습니다.

## Blocking

None.

## Suggestions

**S1. 반대 관점 base/확장 이원화 — 회복탄력성을 위한 합리적 설계.** base counter_arguments는 항상 있는 `/topics/{id}`에서, 확장 근거(무효화·선반영·CONTRADICTING)는 500 가능성이 있는 `/explanation`에서 옵니다. 두 소스를 한 패널에서 합치되 explanation 실패 시 base를 유지하는 구조라, BE의 미분석 토픽 500(#384 리뷰 S1)이 반대 관점 전체를 가리지 않습니다. 스펙의 "반대 관점 필수" 요건을 500 상황에서도 만족시키는 타당한 선택입니다.

**S2. 기여 비율 합계 미표시 — 스펙 취지에 부합.** 기여 요인은 개별 비율(%)만 막대로 보이고 합(≈1.0)을 강조하지 않습니다. 비율은 BE 정량·규칙 산출값이며 FE가 합계를 강제·정규화하지 않는 것이 스펙 §5.10(임의 생성 금지) 취지에 맞습니다.

## Questions

**Q1. explanation query 공유.** `InsightExplanationPanel`과 `CounterViewPanel`이 동일 `useNewsTopicExplanationQuery(topicId)`를 각각 호출합니다. react-query 캐시가 queryKey로 요청을 dedupe하므로 네트워크 호출은 1회이고, 두 패널이 같은 데이터·상태를 공유함을 확인했습니다. 중복 요청 우려가 없습니다.
