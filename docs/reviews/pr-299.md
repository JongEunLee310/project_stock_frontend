# PR #299 로컬 리뷰 — 예상 자금 흐름을 BE 수치 구간 계약에 연결 (#298)

## Review Summary

BE가 지운 필드를 FE가 계속 읽고 있어 화면이 조용히 비어 있던 결함을 고치는 PR입니다. 단일
커밋(`fix: 예상 자금 흐름 수치 구간을 연결한다`)이며 계약 타입·어댑터·위젯 참조·픽스처를
건드립니다. diff는 174줄 추가·12줄 삭제이고, 그중 100줄이 어댑터 테스트입니다.

**결함의 성격이 이번 작업의 전제입니다.** BE #393(PR `project_stock#395`, dev 머지 완료)이
ADR-017에 따라 문자열 라벨 `estimated_range`를 지우고 수치 구간 `estimated_flow`로 교체했는데,
FE `dto.ts`는 옛 필드를 그대로 선언하고 있었습니다. 마이그레이션에서 컬럼 자체가 제거돼 응답에
없는 필드이므로 값은 항상 `undefined`가 되고, 패널은 모든 섹터를 `범위 미제공`으로 떨어뜨립니다.
**타입 검사도 테스트도 이 상태를 통과합니다** — DTO는 와이어를 선언할 뿐 실제 응답과 대조하지
않기 때문입니다. 화면에서 값이 비어 있는 것을 눈으로 보기 전에는 드러나지 않는 종류입니다.

수정은 세 갈래입니다. 첫째, `dto.ts`의 필드를 `estimated_flow`로 교체하고 구간 모양을 이름 붙은
`FundFlowRangeDto`로 뽑았습니다. 시나리오의 `expected_net_flow`가 같은 모양이라 재사용할 자리가
생깁니다. 둘째, 어댑터에 `adaptFundFlowRange`를 두어 구간을 파싱하고 표시 문자열까지 만듭니다.
뷰 타입에는 표시 문자열과 함께 **원시 수치(`low`·`high`·`currency`)를 남겼습니다** — 이후 막대
길이를 값에 비례시킬 때(#294) 문자열을 되파싱하지 않아도 됩니다. 셋째, 위젯은 참조 필드 이름만
바뀌었습니다. compact·비compact 두 표현 모두 같은 자리에 그대로입니다.

이번 리뷰는 표시 규칙의 경계값, 값을 지어내지 않는지, 표현이 실제로 그대로인지, 같은 유형의
결함이 다른 곳에 더 있는지를 축으로 봤습니다.

## Blocking

None.

## Suggestions

**S1. 억 단위로 줄이면 서로 다른 두 값이 같은 라벨이 될 수 있다 — 표시상 문제, 현 범위에서
허용.** `low`와 `high`가 같은지는 **줄이기 전 원시 값**으로 판단하고, 라벨은 줄인 뒤 만듭니다.
그래서 `100000000`과 `100000001`처럼 억 단위 소수 첫째 자리에서 구분되지 않는 두 값은
`1~1억원`으로 표시됩니다. 실제 자금 흐름 전망에서 1원 차이의 구간이 나올 일은 없으므로 지금
막을 이유는 없습니다. 다만 줄인 뒤 라벨이 같으면 하나만 적는 편이 더 정확합니다. #294에서 이
필드를 다시 다룰 때 함께 정리하면 됩니다.

**S2. 원 단위 표시에 소수가 붙을 수 있다 — 실사용에서 발생하지 않음.** 억 미만 분기는
`formatMoney`에 옵션을 넘기지 않아 `ko-KR` 기본값(소수 3자리까지)을 씁니다. BE는 금액을
`Numeric(20,4)`로 저장하므로 `123.4560` 같은 값이 오면 `123.456원`으로 표시됩니다. 자금 흐름
전망의 단위가 억 이상이라 실제로는 닿지 않는 경로입니다. 억 미만 자체가 이 지표에서는 비정상
입력에 가깝습니다.

**S3. `aggregation_windows`·`expected_net_flow`는 이번에도 소비하지 않는다 — 의도된 범위
제한.** BE가 #390·#393에서 함께 추가한 두 필드는 표시할 자리가 없어 DTO 선언조차 하지
않았습니다. 소비하지 않는 선언은 죽은 코드이고, 자리를 만드는 일은 시각화 정합(#294)의 몫이라는
판단입니다. 핸드오프에 명시했고 구현이 그대로 따랐습니다.

## Questions

**Q1. 표시 규칙의 경계에서 값이 깨지지 않는가.** 확인해 해소했습니다. 어댑터 테스트가 억 이상,
억 미만, 음수를 포함한 구간, 비-KRW 통화, `low === high`, `null`, 읽을 수 없는 값 일곱 가지를
덮습니다. 음수 부호가 보존되고(`-2~-1억원`), 통화가 공백이면 `KRW`로 떨어지며, `low`와 `high`가
같으면 `~`로 잇지 않고 하나만 적습니다.

**Q2. 값을 지어내지 않는가.** 확인해 해소했습니다. 구간이 `null`이거나 `low`·`high`를 수로 읽을
수 없으면 뷰 필드가 `null`이 되고 화면은 `범위 미제공`을 유지합니다. 대체 숫자를 만드는 경로가
없습니다. `Number.isFinite` 가드가 있어 `'Infinity'` 같은 문자열도 `null`로 떨어집니다 —
`parseDecimal`은 `Number()` 기반이라 `NaN` 검사만으로는 통과하는 값입니다.

**Q3. 표현이 실제로 그대로인가.** 확인해 해소했습니다. 위젯 diff는 참조 필드 이름 한 줄뿐입니다.
클래스·구조·슬롯 폭 어느 것도 바뀌지 않았습니다.

**Q4. 같은 유형의 결함이 다른 곳에도 있는가.** 구현자가 전수 확인해 추가 발견이 없다고
보고했고, 리뷰에서 `dto.ts`를 다시 훑어 BE 응답에 없는 필드 선언이 남아 있지 않음을
확인했습니다. 다만 **이 결함 유형은 다시 발생합니다.** DTO와 실제 응답을 대조하는 장치가 없는
한, BE가 필드를 지울 때마다 FE는 조용히 빈 값을 표시합니다. 계약 픽스처를 BE 응답에서 생성하는
방식이 근본 해법이지만 이번 범위 밖이며, 별도 판단이 필요한 사안으로 남깁니다.

**Q5. 브랜치가 사용자 디자인 작업과 충돌하지 않는가.** 해소하지 못했습니다. 이 PR은 최신
`main`에서 분기했고, 사용자의 개요 관제 배치 작업(`feat/news-insight-reference-alignment`)은
`FundFlowOutlookPanel`에 compact 분기를 추가하면서 같은 필드를 참조합니다. **이 PR이 먼저
머지되면 그 브랜치는 `estimatedRange`를 참조하는 코드가 남아 타입 검사에서 깨집니다.** 텍스트
충돌 없이 계약만 어긋나는 유형이라 머지 시점에야 드러납니다. 머지 순서와 후속 정합은 개발자
확인이 필요합니다.

## Documentation Impact

문서 갱신은 필요 없습니다. 계약 정본은 BE `docs/designs/307-news-intelligence-phase3.md`이며
#393에서 이미 갱신됐습니다. FE 설계 문서(`docs/designs/198-news-insights.md`)는 화면 구조 문서라
필드 목록을 담지 않습니다.

ADR은 불요합니다. BE ADR-017의 결정을 따라가는 소비 측 정합 작업이며 FE에서 새로 정한 것이
없습니다. 표시 단위를 억으로 줄이는 규칙은 슬롯 폭에 따른 표현 선택이지 구조 결정이 아닙니다.

Failure Record는 이번 PR 기준으로는 불요합니다. 실패한 접근을 대체한 것이 아니라 계약 변경을
따라가지 못한 상태를 메운 작업입니다. 다만 Q4에 적은 결함 유형 — **BE 계약 변경이 FE에서 타입
검사·테스트를 모두 통과한 채 조용히 빈 값이 되는 것** — 은 반복될 성질이므로, 재발 시에는
기록 대상이 됩니다.

## Final Recommendation

머지 가능합니다. 핸드오프의 요구를 항목별로 확인했습니다. 응답에 없는 필드 참조가 0건 남았고,
표시 규칙의 경계 일곱 가지가 테스트로 덮이며, 구간이 없을 때 대체 숫자를 만드는 경로가
없습니다.

범위는 지켜졌습니다. 위젯 변경은 참조 필드 이름 한 줄이고 표현·배치·클래스는 그대로입니다.
소비할 자리가 없는 `expected_net_flow`·`aggregation_windows`는 DTO 선언조차 하지 않아 죽은
코드가 생기지 않았습니다. 다른 위젯·화면은 건드리지 않았습니다. Protected Files는 없습니다.

테스트는 실제 시드값(`800000000000.0000`~`1800000000000.0000`, `KRW`)을 픽스처로 쓰고, 표시
문자열이 `8,000~18,000억원`이 되는 것을 화면 단언으로도 확인합니다. 지어낸 값이 아닙니다.
셀렉터가 깨졌다는 이유로 삭제된 단언은 없습니다.

Blocking은 없습니다. S1·S2는 실사용에서 닿지 않는 표시상의 경계이고, S3은 의도된 범위
제한입니다. Q1·Q2·Q3은 확인해 해소했고, Q4는 재발 방지 장치가 별도 판단 사안으로 남으며,
**Q5는 머지 순서에 대한 개발자 확인이 필요한 항목**입니다.

최종 머지 권한은 개발자에게 있습니다.
