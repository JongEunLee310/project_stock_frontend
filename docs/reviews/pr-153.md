## Review Summary

이슈 #141(리서치 재설계 로드맵 #152의 1단계)을 구현합니다. 기존에 `/research/:symbol` 하나였던 research 라우트를 `/research`(목록)와 `/research/:symbol`(상세) 두 단계로 분리하고, `appRoutePaths.research`를 `/research`로 재정의하면서 `researchDetail: '/research/:symbol'`을 신설합니다.

핵심 메커니즘은 다음 세 부분으로 구성됩니다. 첫째, `navigation.ts`에서 라우트 상수를 재구성하고 사이드바 항목의 `href`를 하드코딩 `/research/NVDA`에서 `appRoutePaths.research`(`/research`)로 교체합니다. 둘째, `src/features/research/` 계층에 `ResearchListRow` 타입·`adaptResearchListRow` 어댑터·`useResearchList` 쿼리를 추가합니다. `useResearchList`는 `/assets?page=1&size=100`으로 등록 자산을 가져온 뒤 자산별 `/assets/{id}/research-summary`를 `Promise.all`로 병렬 조회합니다. summary 조회가 어떤 이유로든 실패하면 catch 블록이 해당 행을 null summary로 합성해 행 전체가 제거되지 않도록 보호합니다. 셋째, `ResearchListPage`가 테이블 렌더·클라이언트 검색 필터·로딩·오류·빈 상태를 처리합니다.

설계 문서(`docs/designs/141-research-list-page.md`)가 명시한 N+1 병렬 조회는 BE 큐 계약(project_stock #266) 전의 의도된 임시 구조로, 이번 리뷰에서는 결함으로 판단하지 않습니다.

기존 소비처 전수 치환은 grep으로 확인했습니다. `DashboardPage`, `DecisionLogPage`, `PortfolioPage`, `SignalsPage`, `WatchlistPage` 다섯 파일이 각자의 `getResearchPath` 헬퍼를 `appRoutePaths.researchDetail.replace(':symbol', symbol)` 방식으로 교체하거나 신규 정의했으며, `src/` 전체에서 `appRoutePaths.research`를 상세 링크 생성에 직접 사용하는 잔존 소비처는 없습니다.

## Suggestions

**S1. `catch` 블록이 모든 예외를 흡수해 네트워크 단절과 summary 미존재를 동일하게 처리합니다**

`useResearchList`의 summary 조회 catch 블록(`} catch { return adaptResearchListRow(asset, null) }`)은 에러 종류를 구분하지 않습니다. summary가 아직 생성되지 않아 404가 반환된 경우와 네트워크가 일시적으로 끊겨 모든 summary 조회가 실패한 경우를 구별할 수 없기 때문에, 후자의 상황에서도 목록이 정상적으로 렌더되고 모든 행의 'AI 판단'이 비어 있는 것처럼 보입니다. BE 계약 상 summary가 없는 자산에 대해 반환되는 에러 코드가 확정돼 있다면(예: `RESEARCH_SUMMARY_NOT_FOUND`), catch 블록에서 `ApiError`의 코드를 검사해 summary 미존재만 흡수하고 나머지는 다시 던지는 방식이 PR #139의 `fetchLatestThesis` 선례와도 일관됩니다. 다만 BE에서 해당 코드가 아직 확정되지 않았거나 1단계 범위에서 허용된 단순화라면 #143 작업 시 함께 처리해도 무방합니다. 심각도: 비차단·후속 처리 권장.

**S2. `/assets?page=1&size=100`이 하드코딩되어 있어 등록 종목이 100개를 초과하면 목록이 잘립니다**

현재 구현은 한 번의 요청으로 최대 100개 자산만 가져옵니다. 운영 중 종목이 100개를 넘을 경우 목록이 조용히 잘려 사용자가 알아채기 어렵습니다. `meta.total`과 응답 건수를 비교해 초과 여부를 감지하거나, 2단계(#143)에서 BE 큐 계약으로 대체할 때 함께 해소하는 방향을 권장합니다. 현 단계에서는 등록 종목이 수십 개 수준이라 즉각적인 위험은 낮습니다. 심각도: 비차단·저비용 관찰, #143 시 해소 권장.

**S3. 검색 입력이 오류·로딩 상태에서도 마운트되지 않으므로 별도 조치는 불필요하나 빈 상태 분기 순서를 점검할 수 있습니다**

현재 조건 분기 순서는 `isLoading → isError → rows.length === 0 → 테이블`입니다. `isLoading`이 false이고 `isError`도 false인데 `data`가 `undefined`인 엣지 케이스(초기 마운트 직후 등)에서는 `rows`가 빈 배열로 평가돼 EmptyState가 렌더될 수 있습니다. TanStack Query의 초기 상태에서 `isLoading`이 true로 시작하므로 실제 노출 가능성은 낮지만, `researchListQuery.isSuccess`를 조건에 포함하거나 `data === undefined`를 명시적으로 처리하면 의도가 더 명확해집니다. 심각도: 비차단·낮은 우선순위.

## Questions

**Q1. 테스트 픽스처의 summary 에러 구조가 BE 실응답과 일치하는지 확인이 필요합니다**

`queries.test.tsx`의 `researchSummaryNotFoundEnvelope`는 `{ data: null, message: '...', error: { code: 'RESEARCH_SUMMARY_NOT_FOUND' }, meta: null }` 형태로 작성되어 있습니다. 이 코드값(`RESEARCH_SUMMARY_NOT_FOUND`)이 실제 BE `error_codes.py`에 정의된 리터럴과 일치하는지 확인이 필요합니다. 현재 catch 블록이 에러 코드를 구분하지 않으므로 테스트 통과에는 영향이 없지만, 향후 S1 방향으로 정밀화할 때 픽스처 코드값이 BE 계약과 달라질 수 있습니다.

**Q2. `DashboardPage`의 `<SectionLink label="자세히 보기" to={getResearchPath('NVDA')}>`가 하드코딩된 NVDA를 가리킵니다**

변경 전에는 `/research/NVDA`로 하드코딩되어 있던 것을 이번 PR에서 `getResearchPath('NVDA')`로 교체했습니다. 라우팅 오류는 해소됐으나 NVDA 심볼 자체가 여전히 하드코딩되어 있습니다. 이 링크가 의도적인 고정 링크인지 아니면 다음 단계에서 동적으로 교체될 예정인지 확인이 필요합니다.
