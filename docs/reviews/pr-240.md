# PR #240 로컬 리뷰 — fix: Signals deep-link 목적지를 /settings로 변경 (#235)

## Review Summary

ADR-014를 FE에 적용하는 3단계의 마지막입니다. 커밋은 두 건이며 핸드오프 문서
(`.codex/tasks/task-092-signals-deeplink-settings.md`) 추가와 구현으로 나뉩니다.

1단계(#233, PR #237)에서 `AlertRuleBuilder`와 `useSearchParams` 기반 쿼리 소비가
`SettingsPage`로 옮겨졌으므로, Signals 카드가 가리키는 목적지도 따라가야 합니다. 변경은
`src/pages/ui/SignalsPage.tsx`에서 `navigate` 대상 상수를 `appRoutePaths.alerts`에서
`appRoutePaths.settings`로 바꾼 한 줄이고, 나머지는 테스트의 기대 경로 갱신입니다.

`URLSearchParams`로 `builder=create`·`symbol=`을 구성하는 코드와 버튼의 표현(라벨 "변화
알림", 접근성 이름 "이 시그널 변화 알림 받기", `FiBell` 아이콘, 3버튼 그리드 내 위치)은
그대로입니다. ADR-013 §1의 "Signals 화면에는 알림 보조 버튼 하나만"과 ADR-014 §4의 "쿼리
규약은 유지하고 도착지만 옮긴다"를 모두 지켰습니다.

리뷰는 두 축으로 봤습니다. 목적지 교체가 기존 계약을 건드리지 않았는지, 그리고 `/alerts`를
가리키는 잔여 deep-link가 남지 않았는지입니다.

## Blocking

None.

## Suggestions

**S1. PR #239와 머지 순서를 함께 관리해야 합니다 — 병합 자체를 막지는 않습니다.** 두 PR은
파일이 겹치지 않아 독립적으로 머지할 수 있지만, 사용자에게 보이는 상태는 순서에 따라
달라집니다. 이 PR만 먼저 머지되면 알림 버튼이 `/settings`로 가서 정상 동작하고 `/alerts`에는
규칙 화면이 잠시 남습니다(중복이지만 고장은 아님). 반대로 #239만 먼저 머지되면 버튼이
`/alerts`로 가서 아무 일도 일어나지 않습니다(고장으로 보임). 둘 중 하나만 먼저 간다면 이
PR이 먼저인 편이 안전합니다.

## Questions

**Q1. `/alerts`를 가리키는 잔여 deep-link가 있는지 확인했습니다.** `src/` 전체를
`appRoutePaths.alerts}?`와 `/alerts?builder` 패턴으로 검색한 결과 남은 곳은
`src/pages/ui/AlertsPage.test.tsx`의 렌더 진입 경로 한 곳뿐이었습니다. 이는 `AlertsPage`가
아직 쿼리를 처리하던 시점의 테스트이고, PR #239가 해당 처리와 테스트를 함께 제거하므로 두 PR이
모두 머지되면 잔여가 사라집니다. `appRoutePaths.alerts` 상수 자체는 사이드바 등 다른 용도로
계속 쓰이므로 제거 대상이 아닙니다. 해소됐습니다.

## Final Recommendation

이슈 #235의 완료 조건을 확인했습니다. 알림 버튼이 `/settings?builder=create&symbol=`로
이동하고, 경로는 상수를 참조해 하드코딩이 없으며, 접근성 이름과 표시 라벨이 기존과
같습니다. 테스트가 새 경로를 단언하도록 갱신됐습니다.

범위가 지켜졌습니다. 프로덕션 코드 변경은 한 줄이고, Protected Files로 지정한
`SettingsPage.tsx`·`AlertsPage.tsx`·`navigation.ts`와 `alert-rule-builder` 내부는 diff에
없습니다.

회귀 위험은 낮습니다. `SettingsPage`의 쿼리 소비 로직은 PR #237에서 이미 테스트로 덮여
있고, 이번 변경은 그 입구를 연결하는 것뿐입니다.

Blocking은 없습니다. Suggestions S1은 머지 순서에 대한 권고이고 Questions Q1은 리뷰 중
검색으로 해소했으므로, 둘 다 병합을 막지 않습니다.
